## 3a 低精度、算子与编译优化

本章回答：在模型功能基本确定后，如何减少一次训练迭代或推理前向的计算、访存和调度成本。低精度改变数值表示，算子优化改变单个计算的执行方式，图编译改变多个计算的组合方式；三者可以协同，但收益不能简单相乘。

文中算例均为解释机制而设的假设，不是论文实测结果。辅助核读记录中的页码按PDF文件从第一页开始计数。公式采用简化模型，忽略项会在相邻文字说明。

### 3a.1 FP16、BF16与FP8混合精度训练

**是什么、解决什么问题。** 混合精度让不同计算与状态使用不同数值格式，在减少显存、内存带宽和矩阵计算成本的同时，控制数值误差。它并非把所有变量统一转换成低位宽：参数主副本、优化器状态、归约或敏感计算仍可能使用FP32。具体保留哪些高精度状态取决于训练实现。

| 格式 | 指数位/尾数位，不含符号位 | 主要数值特征 | 训练中的关注点 |
|---|---|---|---|
| FP32 | 8/23 | 范围大、有效精度高 | 通常用于关键状态或参考基线 |
| FP16 | 5/10 | 范围较窄，近1处精度高于BF16 | 小梯度下溢和大值溢出 |
| BF16 | 8/7 | 指数范围接近FP32，尾数较短 | 常可免去FP16式损失缩放，但仍有舍入误差 |
| FP8 E4M3 | 4/3 | 在8位限制下偏重有效精度 | 张量缩放、异常值与格式变体 |
| FP8 E5M2 | 5/2 | 在8位限制下偏重动态范围 | 舍入误差、缩放与具体硬件支持 |

**怎么工作。** FP16训练常将损失乘以缩放因子S，再反向传播，更新前将梯度除以S。原本可能下溢的小梯度因放大而得到保留；若出现Inf/NaN，动态损失缩放可以跳过该次更新并减小S。FP8通常还要对张量做数值缩放，例如利用当前或历史绝对最大值选择尺度，再转换成FP8。损失缩放与张量量化缩放处理的问题和作用位置不同，不能混为一谈。

**直观例子。** 某层权重只需要很小的更新量；若直接在低精度权重上累加，这个更新可能被舍入掉。保留FP32主权重、在高精度状态上更新，再生成低精度计算副本，可以缓解这一问题。FP8虽然每个值只占1字节，但优化器状态、缩放元数据和转换缓冲区仍存在，整体训练显存通常不会简单降为FP16的一半。

**适用条件与代价。** 大矩阵乘法、匹配的Tensor Core内核和稳定的数值分布有利于获得收益。小矩阵、频繁类型转换、缩放统计和内核启动开销可能抵消收益。BF16不是“永远不溢出”，FP8也不是一个统一不变的格式：需要核对硬件、框架版本、缩放粒度、累加精度和检查点中的缩放状态。

**怎么评价。** 比较达到同一目标损失或精度所需的总训练时间，同时记录tokens/s、峰值显存、溢出/跳步次数、损失曲线和最终任务指标。只比较GEMM峰值算力无法判断训练是否真的更快。依据：[MixedPrecision](../3a_低精度_算子_编译优化/MixedPrecision.pdf)、[FP8Formats](../3a_低精度_算子_编译优化/FP8Formats.pdf)、[FP8LM](../3a_低精度_算子_编译优化/FP8LM.pdf)；实现补充：[NVIDIA FP8缩放说明](https://docs.nvidia.com/deeplearning/transformer-engine/user-guide/features/low_precision_training/fp8_delayed_scaling/fp8_delayed_scaling.html)。

### 3a.2 INT8、INT4与FP8推理量化

**是什么。** 量化是用更少的位表示权重、激活或KV状态。截图中的“NT8”在本解读中按常见术语INT8理解。W4A16表示权重4位、激活16位，W8A8表示权重与激活均8位；这些记号不自动说明累加器精度，也不说明KV缓存位宽。FP8是浮点低精度格式，INT8/INT4通常需要显式量化尺度。

**怎么工作。** 仿射整数方案可简写为`q = clip(round(x/s) + z)`，反量化为`x_hat = s × (q-z)`。s是尺度，z是零点。位宽越低，可表示的离散级数越少；极少数离群值若决定了整个张量的范围，大量普通值会被挤进很少的量化级。按通道或按组缩放可缓解这一问题，但需要更多尺度元数据和相应内核。

**代表方法如何区分。** GPTQ利用校准输入与近似二阶信息，在逐步量化权重时补偿剩余权重的重构误差。SmoothQuant通过等价缩放把激活量化困难转移给更容易量化的权重，适合讨论W8A8。AWQ利用激活统计识别重要权重通道，并通过缩放降低低比特权重量化误差。不能把这些方法都描述成“简单截断小数”。PTQ是训练后量化；QAT是在训练或微调中显式模拟量化误差，两者的准备成本不同。

**算例与瓶颈。** 假设模型有70亿参数，仅权重存储从16位降到4位，理论原始容量由约14 GB降到3.5 GB，均为十进制GB。实际还包括尺度、零点、未量化层、对齐和运行时工作区。若Decode主要受权重读取限制，权重压缩有机会提速；若内核需要昂贵解包、反量化，或者瓶颈是注意力读取长KV，收益可能小得多。

**怎么评价。** 记录模型质量、校准数据代表性、权重/KV总显存、Prefill和Decode分阶段速度，以及端到端TTFT、TPOT。应在相同硬件、输入输出长度和并发条件下比较。依据：[GPTQ](../3a_低精度_算子_编译优化/GPTQ.pdf)、[SmoothQuant](../3a_低精度_算子_编译优化/SmoothQuant.pdf)、[AWQ](../3a_低精度_算子_编译优化/AWQ.pdf)、[FP8PTQ](../3a_低精度_算子_编译优化/FP8PTQ.pdf)。

### 3a.3 算子融合

**问题来源。** 神经网络中许多逐元素运算单独执行时，真正计算很短，却需要多次启动GPU内核，并把中间张量反复写入、读出显存。例如`y = GELU(xW+b)`可拆成矩阵乘、加偏置、激活三个算子。若每一步都生成完整中间结果，显存带宽和启动延迟会占据较大比例。

**怎么工作。** 融合使生产者与消费者尽量在同一内核中执行，复用寄存器或共享内存中的中间值。矩阵乘的epilogue可融合偏置、缩放或激活；多次逐元素操作也可在一次读写中完成。这里减少的是中间数据移动和调度开销，不一定减少数学定义中的运算次数。

**为什么不能无限融合。** 融合过大可能提高寄存器占用、降低并发驻留的线程块数量，还可能引入更多同步，或者失去调用成熟高性能库的机会。若融合后的内核资源需求不适合当前形状，反而会更慢。跨设备通信也不能仅通过普通本地算子融合消除。

**怎么评价。** 对比内核数量、HBM读写量、寄存器占用、设备利用率和端到端时延，并检查数值一致性。应区分冷启动/编译时间与稳态执行。依据：[FlashAttention的访存与融合讨论](../3a_低精度_算子_编译优化/FlashAttention.pdf)、[Triton](../3a_低精度_算子_编译优化/Triton.pdf)、[TASO](../3a_低精度_算子_编译优化/TASO.pdf)。

### 3a.4 注意力算子优化

**问题来源。** 标准稠密注意力可写为`O = softmax(QKᵀ/√d)V`。长度为N的序列通常涉及N×N注意力分数，直接把整张分数矩阵和概率矩阵写入HBM会造成很大的中间数据开销。

**FlashAttention的思路。** 将Q、K、V分块加载到片上存储，逐块计算注意力。在线softmax维护每一行到目前为止的最大值、指数和以及加权输出；遇到新的更大最大值时，对旧累计量重新缩放，使分块累积仍对应完整softmax。这样无需把完整N×N中间矩阵物化到HBM，反向传播还可通过重算中间量减少保存成本。

**重要边界。** 对稠密注意力，FlashAttention通常仍保留二次规模的注意力计算，核心改进是IO与执行组织，不应写成“将所有注意力复杂度降为线性”。“精确注意力”表示不采用稀疏化或近似注意力定义，浮点执行顺序变化仍可能带来数值差异。FlashAttention-2关注工作划分等优化；FlashAttention-3进一步利用特定GPU上的异步执行与低精度能力。

**Prefill与Decode区别。** Prefill同时处理多个查询token，适合大块矩阵运算；单步Decode的查询数很少，却要访问历史KV，常需要不同的并行与归约安排。因此“训练注意力内核很快”不保证长上下文Decode同样理想。评价要分别给出序列长度、批量、头数、头维、数据类型和阶段。依据：[FlashAttention](../3a_低精度_算子_编译优化/FlashAttention.pdf)、[FlashAttention2](../3a_低精度_算子_编译优化/FlashAttention2.pdf)、[FlashAttention3](../3a_低精度_算子_编译优化/FlashAttention3.pdf)、[FlashDecoding](../3b_大模型推理加速/FlashDecoding.pdf)。

### 3a.5 计算图编译

**是什么。** 图编译把模型的高层算子描述转换为适合目标硬件的执行计划。典型过程包括图捕获、形状与数据类型推导、等价图变换、算子融合、布局选择、内存规划、低层代码生成和链接。它关注跨算子的整体计划，和手写一个CUDA内核处于不同层次。

**机制与例子。** 编译器可能删除无效计算、折叠常量，或选择能减少布局转换的算子组合。TASO通过生成并验证图替换规则扩展优化空间；TVM提供从模型到多种硬件的编译路径；TensorIR提供张量程序层面的表示与变换。规则必须满足相应语义前提，例如改变浮点运算结合顺序可能改变舍入结果，不能把数学上的等价无条件当成逐位一致。

**适用条件。** 形状和控制流稳定、同一模型长时间重复运行时，编译成本容易摊薄。高度动态的输入、数据相关分支或未支持算子会产生图中断、回退或多次特化编译。服务中应分别统计首次请求时延和缓存命中后的稳态时延，防止将预热成本隐藏。

**与CUDA Graph的区别。** 图编译可以改变计算和数据布局；CUDA Graph主要复用已经定义的执行依赖、减少重复提交开销。两者可组合，但“使用图”不等于自动完成模型图优化。依据：[TVM](../3a_低精度_算子_编译优化/TVM.pdf)、[TASO](../3a_低精度_算子_编译优化/TASO.pdf)、[TensorIR](../3a_低精度_算子_编译优化/TensorIR.pdf)。

### 3a.6 自动调优

**是什么。** 同一个数学算子可以采用多种分块尺寸、线程映射、流水深度、向量宽度和布局。自动调优是在合法方案中寻找适合具体设备和输入形状的实现，而不是更改模型训练的学习率等超参数。

**怎么工作。** 先定义候选空间，再用启发式或成本模型筛选方案，编译并在设备上测量，利用测量结果继续搜索。Ansor用高层结构和低层细节的分层表示描述候选，并结合进化搜索、学习型成本模型及跨子图的搜索预算分配。Triton使分块程序表达更直接，但写出Triton代码并不保证已经选到最优配置。

**权衡与算例。** 假设调优花费30分钟，稳态每次调用节省1毫秒，则仅按运行时间计算，需要约180万次调用才能摊平调优成本。这是简化算例，未计入开发成本和能源。常见生产方案是离线调优常用形状、保存结果，并为低频或新形状提供稳妥的默认路径。

**怎么评价。** 除最终时延，还要报告搜索时间、候选次数、编译失败率、测量噪声和跨形状泛化。温度、频率、其他任务干扰都会影响测量，不能只取一次偶然的最小值。依据：[Ansor](../3a_低精度_算子_编译优化/Ansor.pdf)、[TensorIR](../3a_低精度_算子_编译优化/TensorIR.pdf)、[Triton](../3a_低精度_算子_编译优化/Triton.pdf)。

### 本章之间如何配合

先用性能剖析定位计算或访存瓶颈，再选择低精度、融合和注意力优化，最后用编译与调优固化实现。例如低比特权重减少了读取量，但解包成为新瓶颈时，应优化反量化与矩阵乘的融合；盲目继续降低位宽未必有效。报告中宜用同一模型、同一质量门槛下的消融实验说明各项贡献。

## 3b 大模型推理加速

本章以自回归、因果注意力的大语言模型为主。编码器模型、非自回归模型和某些混合架构的状态与调度方式可能不同。先理解一次请求的生命周期，才能判断优化到底减少了哪一段时间。

### 3b.1 请求进入、Prefill、KV Cache、Decode与输出

**生命周期。** 一次典型请求依次经历接入与排队、分词及输入准备、Prefill、反复Decode、结果流式发送及状态释放。KV Cache是贯穿Prefill与Decode的状态，不是与它们并列的独立计算阶段。流式输出通常从Prefill产生第一个输出token后就开始，而不是等整个Decode结束才发送。

**Prefill在做什么。** 对输入的多个token并行执行前向计算，生成各层的K、V，并得到用于采样第一个输出token的分布。由于因果掩码，位置i只关注自身及之前的位置，但这些位置的计算仍可以在同次前向中组织成大矩阵运算。大输入和适当批量下，Prefill常更容易发挥计算能力；短输入、小模型和特殊硬件上不能一概断言它一定计算受限。

**Decode在做什么。** 每轮用新token产生新的Q、K、V，查询历史KV，然后预测下一个token。历史token的各层K、V不必从头重复计算。这减少了重复工作，但历史KV仍要被读取；上下文越长，KV访问和注意力计算压力通常越大。小批量Decode常受权重读取、KV读取或启动开销限制。

**KV容量算例。** 简化地，单条序列完整KV容量约为`M = 2 × L × T × H_kv × d × b`。L为层数，T为缓存token数，H_kv为KV头数，d为头维，b为每元素字节数，系数2对应K和V。若L=32、T=8192、H_kv=8、d=128、b=2，则约为1 GiB。这里未计页对齐、复制、分片、滑动窗口和框架额外状态。GQA/MQA会改变KV头数，因此不能总用查询头数代入。

**指标。** TTFT包含排队和首token之前的处理；TPOT常按后续输出的平均时间计算，具体是否含网络开销要注明。ITL/TBT描述相邻token的间隔，能揭示平均TPOT掩盖的长停顿。依据：[PagedAttention](../3b_大模型推理加速/PagedAttention.pdf)、[DistServe](../3b_大模型推理加速/DistServe.pdf)、[SLOMetrics](../4c_推理高可用_SLO/SLOMetrics.pdf)。

### 3b.2 Continuous batching：连续批处理

**问题。** 静态请求批处理通常先凑一批，再等这一批都完成后启动下一批。若A生成20个token、B生成200个token，A先完成后留下的资源不能及时填充，等待中的C仍可能无法进入。不同输出长度造成“短请求等长请求”。

**机制。** 连续批处理把调度粒度缩小到迭代：每轮结束检查完成状态，释放已结束请求，纳入新请求。Orca的迭代级调度与选择性批处理提供了这一方向的基础。实现中，batch成员、长度和KV映射都可能动态变化，因此它需要与缓存分配和内核执行协同。

**新矛盾。** 新请求的Prefill可能很长，把它直接插入运行中的Decode会使所有正在输出的请求停顿。Chunked Prefill将长输入分成若干段，SarathiServe在每轮中限制Prefill工作量，并与Decode组成批次。它并未消除长输入的计算，只是把阻塞分散到多个调度周期。

**怎么选择。** 离线批量生成偏重吞吐，可容忍较大批量；在线对话要同时保护首token与后续token间隔。批量token预算、最大并发数和每轮Prefill大小应结合SLO调节。批量越大通常越能摊薄权重读取，但可能提高等待时间和KV占用，不存在统一最佳值。依据：[Orca](../3b_大模型推理加速/Orca.pdf)、[SarathiServe](../3b_大模型推理加速/SarathiServe.pdf)。

### 3b.3 Paged KV Cache：分页KV缓存

**问题。** 请求最终会生成多少token事先未知。若预留一个很大的连续显存区，会浪费没有实际使用的空间；若频繁申请不同大小的连续块，又容易出现碎片。大量并发时，“总空闲显存足够，却没有合适连续空间”会限制可接纳请求数。

**机制。** PagedAttention按固定token块管理KV：逻辑上连续的token块映射到物理上不连续的显存块，注意力内核通过块表找到数据。序列增长时按需追加块，完成时回收；某些共享前缀或分支生成场景可以共享物理块，写入时采用相应的复制机制。这是一种结合内存管理与注意力内核的设计。

**算例。** 假设每块16个token，一条序列实际占用35个token，需要3块，最后一块有13个未使用位置。它仍有内部碎片，但不会为假设的最大输出长度预留完整空间。块越小，尾块浪费越少，块表与索引成本通常越高；块越大则相反。

**边界。** GPU上的分页KV管理不等价于操作系统自动把显存换出到磁盘；是否支持CPU交换、远端KV等是另外的实现能力。分页本身也不压缩每个KV元素，更不会消除历史注意力访问。评价需看可承载并发、碎片率、分配开销、内核访问效率及端到端goodput。依据：[PagedAttention](../3b_大模型推理加速/PagedAttention.pdf)。

### 3b.4 Prefix caching：前缀缓存

**问题与原理。** 多个请求可能共享系统提示、长文档或多轮对话的开头。如果模型和执行条件一致、前缀token完全相同，因果模型中该前缀的KV可被复用。新请求只需补算不共享的后缀，从而减少重复Prefill。SGLang的RadixAttention用基数树组织可共享前缀；分页缓存也可以通过块哈希识别共享部分。

**例子。** 十个问题都基于同一份8000-token文档，区别只是后面的几十个问题token。若文档位于相同前缀位置，首次请求计算文档KV，后续请求可复用。若文档前插入了不同的时间戳，token前缀提前出现差异，后续文档文本即使相同，也不能按普通前缀缓存直接复用。

**命中条件。** 不能只比较“文本意思相似”。还要考虑分词、模型权重、适配器、位置编码、缓存格式，以及多模态输入等影响状态的因素。工程实现还应明确跨租户的缓存共享策略。这些条件不同，复用的状态可能不正确或不适合共享。

**收益边界。** 缓存命中主要节省已有前缀的Prefill，后续Decode仍需读取历史KV。保留缓存也占显存，可能挤压正在执行的请求。评价应包括token加权命中率、节省的Prefill token量、冷/热启动差异、回收策略和显存压力；只报告“请求命中率”容易夸大短前缀命中的价值。依据：[SGLang](../3b_大模型推理加速/SGLang.pdf)、[PagedAttention](../3b_大模型推理加速/PagedAttention.pdf)、[vLLM前缀缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)。

### 3b.5 PD disaggregation：Prefill与Decode分离

**为什么拆分。** Prefill与Decode对计算、带宽和批处理的偏好不同。放在同一实例上会互相干扰，而且两阶段被迫采用相同的资源份额。PD分离用不同实例或资源池负责两阶段，允许独立选择并行度、硬件配置和扩缩容比例。

**怎么工作。** Prefill实例处理提示并产生KV，然后将需要的状态传到Decode实例，由后者持续生成token。调度器不仅选择“哪张卡空闲”，还需要考虑两阶段排队、KV传输路径、状态布局及可用容量。DistServe强调在SLO约束下配置与放置两阶段；Splitwise从阶段拆分讨论不同资源组合；PDServe补充规模部署经验。

**传输是否值得。** 若要迁移1 GiB KV，实际有效带宽为25 GiB/s，仅理想数据传输就约需40毫秒，还未计入排队、序列化、布局转换与同步。能否获益取决于分离后减少的干扰与排队是否超过这些成本。并行分片布局不同还可能需要状态重排，因此不能只引用网卡标称带宽。

**适用范围。** 中高负载、阶段比例可预测且互联充足时更值得考虑。短请求、低并发或网络不足时，共置可能更简单且更快。两阶段分开后，一侧扩容也可能把瓶颈转移到另一侧。评价至少包含每GPU goodput、TTFT、Decode尾延迟、KV传输量和两池利用率。依据：[DistServe](../3b_大模型推理加速/DistServe.pdf)、[Splitwise](../3b_大模型推理加速/Splitwise.pdf)、[PDServe](../3b_大模型推理加速/PDServe.pdf)。

### 3b.6 Speculative decoding：推测解码

**为什么有效。** 自回归生成需要串行运行目标模型。推测解码先用便宜的草稿模型或预测头提出多个候选token，再由目标模型并行验证这些候选，使一次较昂贵的目标前向有机会推进多个输出位置。

**精确采样机制。** 在经典草稿分布q、目标分布p的方案中，草稿候选x按`min(1,p(x)/q(x))`接受；第一次拒绝后，从适当归一化的正残差`max(p-q,0)`中重新采样，丢弃无效候选后缀。若整段接受，还可以按算法生成额外token。满足算法前提时保持的是目标输出的概率分布，不是保证在相同随机种子下逐token完全一样。贪心解码有相应的确定性验证规则，不能直接混用采样公式。

**不同路线。** 原始推测解码使用独立小模型；Medusa引入多个预测头；EAGLE使用特征预测；SpecInfer组织树状候选并验证。它们在训练需求、候选结构、验证内核和精确性保证上不同，不能把“有草稿”自动等同于严格分布无损。

**收益模型。** 简化地，平均每个接受token的成本可看作`(草稿成本 + 目标验证成本 + 管理成本) / 本轮有效推进token数`。草稿足够便宜、接受率足够高且验证能有效并行时，才有明显收益。高批量时目标GPU可能已很忙，验证额外候选反而占用资源；因此单请求延迟提升不代表整体吞吐也提升。

**怎么评价。** 记录接受率、平均有效推进长度、草稿时延、验证时延、显存额外占用、目标分布/任务质量，以及不同并发下的TTFT和TPOT。依据：[SpeculativeDecoding](../3b_大模型推理加速/SpeculativeDecoding.pdf)、[SpeculativeSampling](../3b_大模型推理加速/SpeculativeSampling.pdf)、[Medusa](../3b_大模型推理加速/Medusa.pdf)、[EAGLE](../3b_大模型推理加速/EAGLE.pdf)、[SpecInfer](../3b_大模型推理加速/SpecInfer.pdf)。

### 本章的组合关系

连续批处理决定谁在什么时候执行；分页KV解决状态分配；前缀缓存避免重复Prefill；PD分离改变两阶段部署；推测解码减少串行目标步数。它们分别优化不同环节，但会争用相同的显存、网络和计算资源。建议先建立无缓存、无草稿的基线，再逐项开启功能，并在固定SLO和质量要求下比较。

## 3c Diffusion与HPC-AI优化

这两个方向都可以减少昂贵的重复计算，但优化对象不同。Diffusion主要围绕多次去噪网络调用；HPC-AI既包括用学习模型加速数值计算，也包括仿真、训练、推理共同组成的工作流。

### 3c.1 Diffusion多步采样与步数压缩

**问题来源。** 扩散模型通常从噪声出发，沿一系列时间步逐渐获得样本。每一步往往都要调用大型去噪网络。即使单次前向已经高效，重复几十次乃至更多次仍会带来较长生成时间。直观地，总时间可以近似分成网络调用总时间、采样器计算和其他处理三部分。

**怎么减少步数。** DDIM构造不同于原始逐步随机采样的生成过程；DPM-Solver利用扩散模型对应微分方程的结构，解析处理部分项并对其余项作高阶近似，用较少网络评估推进更大的时间间隔。关键不只是“每隔几个步跳一次”，而是设计能够控制大步长误差的更新规则。

**步数不等于网络调用次数。** 高阶求解器的一步可能包含多次模型评估；Classifier-Free Guidance的条件/无条件评估可能合批，也可能分开。因此应同时报告采样步数、NFE（函数/网络评估次数）、每次评估的实际批量和总延迟。仅把50步改成20步，并不能保证端到端速度提高2.5倍。

**适用条件与质量代价。** 无需再训练的采样器适合已有模型，但减少步数会改变离散化误差，对指导强度、噪声日程、预测参数化方式和任务可能敏感。评价图像可看FID、文本一致性及人工比较，视频还要看时序一致性；不同数据集与模型的指标不能直接横比。依据：[DDIM](../3c_Diffusion与HPC_AI/DDIM.pdf)、[DPMSolver](../3c_Diffusion与HPC_AI/DPMSolver.pdf)、[DPMSolverPlus](../3c_Diffusion与HPC_AI/DPMSolverPlus.pdf)。

### 3c.2 蒸馏与一致性模型

**是什么。** 蒸馏把一个多步、较慢的教师生成过程压缩到更少步骤的学生模型。与只更换采样器不同，它通常要更新模型参数，因此把一部分推理工作转化成了离线训练成本。

**渐进蒸馏机制。** 以教师的两次更新结果为目标，训练学生用一次更新近似达到相同位置；学生再成为下一轮教师，逐轮减少所需步骤。教师轨迹质量与误差传递是关键，学生不是通过“删除中间层”直接得到。Consistency Models则学习把同一生成轨迹上的不同噪声状态映射到一致的输出，支持一步或少步生成；具体可以采用蒸馏或相应训练方式。Latent Consistency Models把相关思路用于潜空间生成。

**适用场景。** 模型被长期、高频调用时，离线蒸馏成本可以摊薄；模型频繁更换或只运行少量请求时，准备成本可能不划算。领域、分辨率、条件控制和指导强度改变后，不能假定原有少步质量保持不变。

**怎么评价。** 在固定质量门槛下比较推理时延，并列出教师成本、学生训练成本、所需训练数据及推理频率。简化摊销条件是`调用次数 × 每次节省时间 > 蒸馏投入时间`，但现实中还需区分训练GPU与服务GPU的成本。依据：[ProgressiveDistillation](../3c_Diffusion与HPC_AI/ProgressiveDistillation.pdf)、[ConsistencyModels](../3c_Diffusion与HPC_AI/ConsistencyModels.pdf)、[LatentConsistency](../3c_Diffusion与HPC_AI/LatentConsistency.pdf)。

### 3c.3 跨步特征复用与缓存

**为什么能复用。** 相邻去噪步骤的中间特征通常具有一定相似性。若每一步都完整重算，可能重复处理变化很小的信息。缓存方法选择部分步骤或网络部分重新计算，其余时候复用已有结果，从而减少每一步的实际工作量。

**代表机制。** DeepCache利用U-Net结构，在保持部分低层特征更新的同时复用高层特征。TeaCache利用时间步相关输入估计输出变化，依据变化累积等机制决定何时重算。这些方法的核心是近似复用：新时间步的真实输出一般并不与旧输出完全相同。

**与LLM前缀缓存的区别。** 相同模型、相同前缀条件下的LLM前缀KV复用，可以避免对同一计算的重复执行；Diffusion跨步缓存面对的是不同时间步和不同噪声状态，依赖相似性而不是输入相等。因此要独立评估误差和视觉质量，不能因为叫“缓存”就称为完全无损。

**权衡。** 缓存得越久，计算越少，陈旧误差也可能越大；重算过于频繁则收益有限。缓存还占用显存，可能降低批量。少步采样已经使相邻时间点更远，和缓存一起使用时未必能叠加全部收益。DistriFusion进一步说明分布式扩散中的复用与通信组织也存在关联。

**怎么评价。** 记录实际跳过的网络块或调用比例、缓存占用、端到端速度、质量变化，以及复杂运动、细节丰富场景等困难样例。依据：[DeepCache](../3c_Diffusion与HPC_AI/DeepCache.pdf)、[TeaCache](../3c_Diffusion与HPC_AI/TeaCache.pdf)、[DistriFusion](../3c_Diffusion与HPC_AI/DistriFusion.pdf)。

### 3c.4 AI代理模型加速或替代数值求解

**是什么。** 传统数值求解器根据方程、网格、边界条件等迭代计算结果；代理模型利用训练数据学习从条件到解或部分中间量的映射。训练完成后，一次神经网络前向可能提供近似解、初始猜测、闭合项或候选筛选结果，从而减少昂贵求解器调用。

**代表方法。** FNO通过傅里叶空间中的参数化变换学习函数到函数的映射；DeepONet通过不同网络分支表达输入函数和输出位置之间的算子关系。GraphCast提供学习型天气预报案例。这里“算子”是函数空间之间的映射，与GPU执行中的加法、矩阵乘等“算子”不是同一个层次的概念。

**三种使用层次。** 一是直接预测近似结果；二是给传统求解器提供初值、校正项或局部替代；三是先用代理筛掉低价值候选，只对少数候选运行高保真仿真。第二、第三种往往更容易保留原求解流程中的校验机制，但具体方案仍需按问题设计，不能从某一代理论文自动推导出收敛保证。

**算例。** 假设一次高保真仿真耗时1小时，代理推理耗时1秒。若只有一次求解任务，生成训练数据的数千小时可能并不值得；若需要对同类参数做百万次扫描，离线训练成本可能被摊薄。速度快并不意味着物理误差可以接受，应在同一误差标准下比较。

**怎么评价。** 除相对L2误差，还可按任务考察守恒量、边界条件、长时间滚动稳定性、分布外参数和网格迁移。神经算子支持不同离散化的表达，不等于自动保证任意分辨率、任意物理条件下的准确率。依据：[FNO](../3c_Diffusion与HPC_AI/FNO.pdf)、[DeepONet](../3c_Diffusion与HPC_AI/DeepONet.pdf)、[GraphCast](../3c_Diffusion与HPC_AI/GraphCast.pdf)。

### 3c.5 仿真—训练—推理混合工作流编排

**为什么不只是运行一个模型。** 在自适应科学计算中，仿真产生数据，训练更新模型，推理选择下一批仿真条件，形成持续反馈。仿真可能是MPI程序，训练使用GPU，分析任务使用CPU，各阶段耗时、资源形态和完成节奏都不同。

**同步与异步。** 同步流程等待全部仿真完成后统一训练和决策，版本容易管理，但慢任务会让其他资源空闲。异步流程让仿真持续生产数据，训练与推理并行推进，能降低等待，但必须处理数据背压、模型版本、状态陈旧度及任务依赖。不能为了“异步”让推理读到尚未完整发布的模型。

**系统机制。** SmartSim借助编排与内存数据服务连接仿真和在线推理；DeepDriveMD展示学习模型引导分子模拟；Colmena以事件驱动的控制逻辑协调任务提交、模型调用与学习。它们不是简单把一个Python脚本替换成工作流图，而是管理长期运行的跨程序数据流和反馈。

**示例。** 一组分子模拟持续输出构象，训练端更新表示模型，推理端发现值得探索的状态，再启动下一批模拟。工作流需要记录每次决策使用的模型版本和输入数据，否则难以解释某次仿真为何被选择。若数据产生速度超过消费速度，还要缓存、丢弃过期数据或降低生产速率，具体取舍由科学目标决定。

**怎么评价。** 首要指标可用time-to-solution，即达到科学目标或收敛条件所需总时间。辅助指标包括节点利用率、队列等待、状态传输量、模型陈旧度和有效样本数量。单个神经网络推理更快，不代表整个科学发现流程更快。依据：[SmartSim](../3c_Diffusion与HPC_AI/SmartSim.pdf)、[DeepDriveMD](../3c_Diffusion与HPC_AI/DeepDriveMD.pdf)、[StreamingAIHPC](../3c_Diffusion与HPC_AI/StreamingAIHPC.pdf)、[ColmenaExascale](../3c_Diffusion与HPC_AI/ColmenaExascale.pdf)。

### 本章的比较建议

| 路线 | 主要减少什么 | 通常是否新增训练 | 首要风险 |
|---|---|---|---|
| 更换采样器 | 达到质量要求所需网络评估次数 | 否 | 大步长误差与配置敏感性 |
| 蒸馏/一致性学习 | 推理步骤 | 通常是 | 训练成本与学生质量 |
| 特征缓存 | 每步重复计算 | 所列缓存方法通常不需要 | 陈旧特征造成近似误差 |
| 数值代理模型 | 高保真求解或其中部分计算 | 是 | 泛化与物理约束 |
| 混合工作流 | 等待、搬运和低价值计算 | 由应用决定 | 状态一致性与反馈失效 |

## 4a 集群监控与故障诊断

大规模同步训练中，一台机器的异常可能放大为整个作业的停顿。监控回答“发生了什么”，性能剖析回答“时间花在哪里”，诊断进一步判断“为什么发生”，隔离则将定位结果转化为调度动作。只有记录指标而没有后续处理闭环，不能称为完整容错能力。

### 4a.1 性能剖析工具与多层可观测性

**需要观察哪些层。** 应用层关注训练step时间、损失和token吞吐；框架层关注算子、数据加载、前反向与优化器；设备层关注GPU频率、内存、温度和内核；通信层关注集合通信、链路计数器与网络拓扑。单个GPU利用率无法串起这些层之间的因果关系。

**工具如何分工。** PyTorch Profiler帮助把高层算子、形状、CPU与CUDA活动关联；Nsight Systems用于查看跨CPU线程、CUDA流与GPU内核的时间线；DCGM提供设备遥测及诊断能力。需要时再对个别内核做更细分析。工具输出中的“等待很久”可能是上游迟到造成的，而不是等待位置自身有问题。

**诊断示例。** 某次迭代变慢，GPU时间线显示两段计算之间有空档。若CPU正在等待数据，则可能是存储或数据处理问题；若CPU已提交任务但设备流在等待事件，则要看依赖；若一批rank都在集合通信等待，需找出最晚进入的rank。相似的“GPU空闲”表象对应不同根因。

**开销与部署方式。** 对所有节点持续采集完整堆栈和每个内核可能产生显著开销与大量数据。较合理的工程思路是常驻低开销指标，检测异常后触发短窗口深度采样，并对齐step编号和时间。该流程是综合建议，不是说所有论文都采用同一实现。

**评价指标。** 采集开销、时间精度、覆盖粒度、异常窗口保留率，以及能否定位到具体rank、设备或操作。依据：[MegaScale](../4a_监控_故障诊断/MegaScale.pdf)、[Holmes](../4a_监控_故障诊断/Holmes.pdf)；工具：[Nsight Systems](../官方工程文档/NsightSystems.html)、[DCGM](../官方工程文档/DCGM_Diagnostics.html)、[PyTorch Profiler](https://docs.pytorch.org/docs/stable/profiler.html)。

### 4a.2 慢卡：设备仍工作但性能下降

**是什么。** 慢卡并不一定离线或报致命错误，而是相同工作明显比同类设备慢。可能原因包括降频、热限制、功耗限制、硬件退化、错误处理开销或其他工作负载竞争。GPU“有利用率”不代表它以正常速度完成工作。

**怎么检测。** 先控制工作负载、形状、精度和并行角色，再比较设备的计算时延、频率、带宽及错误信号。若同一rank总在某张卡上运行，软件角色与硬件身份是混杂因素，可以在可控环境中交换角色或使用隔离基准复测。不能仅按一个全局固定阈值判断不同型号GPU。

**主动验证的价值。** SuperBench讨论灰故障，即系统仍提供功能但性能或可靠性已经退化。针对计算、内存和通信等路径的测试能暴露部分问题，而单一通用压力测试可能漏掉真实训练特有的触发条件。Minder则利用机器之间指标模式的相似性及异常持续性检测故障机器。

**如何处理。** 对瞬时波动保留观察窗口，避免频繁迁移；对持续且可复现的异常，降低调度权重或隔离复检。处理决策应权衡继续运行的损失与迁移/恢复开销。评价要记录检测延迟、误报、漏报和隔离后作业吞吐是否恢复。依据：[SuperBench](../4a_监控_故障诊断/SuperBench.pdf)、[Minder](../4a_监控_故障诊断/Minder.pdf)、[MegaScale](../4a_监控_故障诊断/MegaScale.pdf)。

### 4a.3 慢链路：通信瓶颈与根因定位

**是什么。** 慢链路可能位于GPU互联、PCIe、网卡或交换网络，也可能实际来自拥塞、拓扑绕行和配置问题。其表现常是集合通信时间上升，但集合通信慢不一定由网络造成：某个rank计算慢、迟到，同样会使其他rank显示“通信等待”。

**定位顺序。** 首先区分“各rank进入通信的时间差”与“都已进入后的通信执行时间”。前者更像上游计算、输入或调度问题；后者更值得检查传输路径、消息大小和链路指标。再进行成对带宽/时延测试，并与作业拓扑、网卡错误或重传信号交叉验证。

**算例。** 15个rank在100毫秒进入AllReduce，1个rank在180毫秒才进入。其他rank多出的约80毫秒等待不能直接归为网络传输慢。如果全部rank同时进入仍明显变慢，才应进一步检查通信算法、消息大小、路径拥塞等问题。这个算例说明的是排查逻辑，不是某篇论文的测量。

**工程边界。** 高吞吐压力测试会占用网络，可能反过来干扰生产作业；应明确测试窗口和范围。评价要区分单链路带宽、集合通信有效带宽及端到端迭代时间，不能只用网络设备的标称速率证明通信正常。依据：[MegaScale](../4a_监控_故障诊断/MegaScale.pdf)、[SuperBench](../4a_监控_故障诊断/SuperBench.pdf)、[Holmes](../4a_监控_故障诊断/Holmes.pdf)。

### 4a.4 落后者定位：从症状找到关键路径

**落后者与慢卡的关系。** 落后者是相对进度慢的参与者，可能由慢卡导致，也可能来自数据长度不均、MoE路由负载不均、CPU抢占、数据加载、网络或编译预热。因此“落后者”首先是一种系统行为，不能直接当作硬件故障标签。

**为什么规模越大越敏感。** 在简化同步阶段中，完成时间受`max(t₁,t₂,…,tₙ)`约束。大多数rank更快不能抵消最慢rank的等待。真实混合并行系统还存在流水重叠与跨阶段依赖，应分析关键路径，而不是机械相加所有算子时延。

**定位方法。** 以同一训练阶段或相同角色为比较基准，将异常step映射到rank，再细分到数据、计算和通信阶段，结合持续性、相似性与拓扑缩小范围。不同流水线阶段本来就有不同工作量，未经角色归一化的横向比较容易误报。Minder提供了指标相似性与持续性的具体检测思路；Holmes用于研究大规模训练中的异常定位。

**何时需要干预。** 短暂落后可由后续调度自然消化，持续落后则可能使累计损失超过重新部署成本。若根因是输入长度或专家负载，替换机器往往无效，应调整分配；若根因是设备退化，调度优化可能只能掩盖症状。评价包括定位准确度、定位耗时及修复后有效训练时间。依据：[Minder](../4a_监控_故障诊断/Minder.pdf)、[Holmes](../4a_监控_故障诊断/Holmes.pdf)、[MegaScale](../4a_监控_故障诊断/MegaScale.pdf)。

### 4a.5 主动隔离与健康状态闭环

**是什么。** 主动隔离是在故障完全中断作业之前，或明确识别故障之后，把可疑设备、节点或路径从可调度资源中移出。它需要检测证据、调度器和恢复机制共同参与，而不是简单“杀掉进程”。

**建议状态流程。** 可设计为健康、可疑、排空/隔离、复检、恢复使用几个状态。排空表示不再接新工作，尽可能让已有任务完成或迁移；同步训练常不能独立排空某个rank，此时需要协调检查点与替换。隔离粒度可从单GPU到整机，取决于错误是否关联共享的PCIe、网卡或供电路径。

**降低误伤。** 一次噪声峰值不应自动触发大范围隔离。可组合重复异常、跨指标证据和复测结果，并设置迟滞，避免设备反复进入退出资源池。复检通过后也可先小流量验证。上述是工程设计建议，具体阈值必须结合业务和硬件测定。

**静默错误的特殊性。** 静默数据损坏可能没有明显性能下降，却影响训练结果。仅检测“是否慢”无法覆盖这一类错误，需要数值一致性、针对性测试或其他结果层检查。不能用一次训练损失波动直接断定硬件损坏，也不能因无报警便确认所有结果正确。相关生产研究可进一步阅读SDCsInTheWild。

**怎么评价。** 误隔离资源量、复检时间、同故障复发率、资源可用率和训练有效时间。主动隔离提高质量的同时也消耗容量，因此应与热备、容量预留及恢复策略联动。依据：[SuperBench](../4a_监控_故障诊断/SuperBench.pdf)、[TPUResiliency](../4a_监控_故障诊断/TPUResiliency.pdf)、[SDCsInTheWild](../4a_监控_故障诊断/SDCsInTheWild.pdf)。

### 本章可用于报告的闭环

`指标异常 → 对齐训练阶段 → 定位设备/链路/软件环节 → 确认故障类型 → 选择继续、迁移或恢复 → 复检并更新资源健康状态`

每一步都应保留证据和时间戳。若没有修复后的复测，最多证明“发现了相关异常”，尚不能充分证明根因判断正确。

## 4b Checkpoint与训练恢复

检查点保存的是可恢复的训练状态。只有模型权重通常足以部署推理，却不足以精确续训；训练恢复还可能需要优化器状态、学习率调度器、全局步数、梯度缩放、随机数、数据加载进度及并行分片元数据。若在梯度累积中途保存，还需定义如何处理尚未完成的更新。

### 4b.1 分布式检查点

**问题。** 大模型状态分布在很多设备上。把所有分片集中到一台机器再保存，会形成内存与IO瓶颈。分布式检查点让多个rank并行写出各自持有的状态分片，用元数据描述逻辑张量、切片范围与文件位置。

**怎么保证可用。** 一个检查点需要代表同一逻辑训练时刻。实现可以先冻结一致的状态视图，各rank写临时分片，确认必要分片完成后再提交清单或完成标记。具体协议因系统而异，但核心要求相同：恢复端不能把一部分新分片和一部分旧分片混合使用，也不能把“文件目录已存在”当成检查点完整。

**重分片。** 如果保存时采用8路分片、恢复时采用4路分片，恢复系统必须按逻辑张量关系读取并重组，而不是简单给每张卡分配两个文件。ByteCheckpoint讨论不同并行配置下的检查点使用；PyTorch DCP提供相关分布式状态保存与加载能力，支持范围仍需按模型、状态和版本核对。

**指标与边界。** 记录总状态大小、各rank写入偏斜、并行IO带宽、元数据开销、检查点完成时间与恢复时间。增加写入并发可能压垮共享文件系统；不是rank越多保存就越快。依据：[ByteCheckpoint](../4b_检查点_训练恢复/ByteCheckpoint.pdf)、[PyTorch DCP](https://docs.pytorch.org/docs/stable/distributed.checkpoint.html)。

### 4b.2 异步检查点

**是什么。** 将保存流程的一部分放到后台，让训练尽快继续。典型路径包括GPU状态形成一致快照、搬运到CPU暂存区，再由后台线程或进程写入存储。异步落盘、异步GPU到CPU拷贝和完全异步保存不是同一个承诺。

**一致性是关键。** 若后台仍在读参数，而优化器已经原地修改参数，可能得到跨训练步混杂的快照。系统需要不可变副本、同步事件或其他一致性机制。只有当前状态已被安全隔离后，才可以在不破坏这次快照的前提下继续更新。调用返回也不表示已经持久化，故障恢复应以完成状态为准。

**代价从哪里来。** 快照会消耗额外CPU内存、固定页内存和GPU到CPU带宽；后台写入会与数据读取竞争IO；远程保存还可能争用训练网络。若生成检查点的速度长期快于落盘速度，积压会持续增长。需要限制并发保存数或施加背压，不能无限排队。

**如何评价。** 分别测量训练阻塞时间、后台完成时间和并发保存时的训练降速。例如阻塞仅100毫秒但落盘需30秒，不能直接宣称30秒内任意故障都能恢复到该快照。CheckFreq讨论细粒度保存和流水化；PyTorch异步教程提供暂存与后台保存的具体接口边界。依据：[CheckFreq](../4b_检查点_训练恢复/CheckFreq.pdf)、[PyTorch异步检查点](../官方工程文档/PyTorch_AsyncDCP.html)。

### 4b.3 增量检查点与保存频率

**是什么。** 相对一个已保存基线，仅记录变化部分。可以是被更新的张量块、专家参数、字节差分或经过压缩的变化量，不同系统的“增量”定义不同。恢复时需要基线加相关增量，或事先把它们合并成完整状态。

**为何稀疏更新更有利。** 推荐模型的巨大嵌入表可能每轮只更新少量条目，CheckNRun利用这一特征降低写入量。稠密Transformer训练中大部分参数与优化器状态每步都变化，按“是否变化”筛选未必能省很多。MoE稀疏激活也不自动保证所有训练状态都稀疏变化，要核对具体更新与保存设计。

**恢复链的权衡。** 保存100次小增量可能很省写带宽，但恢复要逐个读取、校验和重放；任意必要环节损坏都可能使该恢复链不可用。因此通常需要周期性完整基线、增量合并和保留策略。压缩若是有损的，还必须验证续训行为，而不能只验证文件能读出来。

**频率的简化推导。** 设一次保存等效开销C、间隔τ、故障率λ，在故障独立且近似均匀落在间隔内、开销较小等假设下，每单位时间的保存与重做损失可近似为`C/τ + λτ/2`。对τ求极值得`τ ≈ √(2C/λ)`。这只是理解权衡的模型；真实系统还有恢复时延、故障相关性、异步干扰、状态大小变化及多级存储，不应直接照搬该值。

**评价。** 写入量减少比例、增量链长度、恢复时间、CPU压缩开销、状态正确性与实际浪费的训练工作。依据：[CheckNRun](../4b_检查点_训练恢复/CheckNRun.pdf)、[CheckFreq](../4b_检查点_训练恢复/CheckFreq.pdf)、[MoEvement](../4b_检查点_训练恢复/MoEvement.pdf)、[TierCheck](../4b_检查点_训练恢复/TierCheck.pdf)。

### 4b.4 原地重启与局部恢复

**原地重启是什么。** 在原节点或原有资源布局上重新启动故障进程，从一个有效状态恢复。它适用于暂时性进程或软件故障、设备仍健康的情形。若根因是硬件故障或确定性软件错误，反复原地重启可能只会重复失败，需要替换设备或修复问题。

**重启成本不只是读权重。** 完整过程包括检测、决定恢复点、清理旧进程、启动框架、建立通信组、加载模型与优化器、恢复数据位置、预热内核，以及重新加入训练。把存储加速到很快之后，通信初始化或框架预热可能成为主要瓶颈。

**局部恢复的难点。** 同步训练中某个rank失败可能使集合通信组失效，不能简单让它重新启动后继续使用其他rank的旧通信句柄。只恢复受影响部分，需要存活副本、状态版本协调和可重建的通信关系。SWIFT研究利用状态副本及日志等机制减少恢复工作；Gemini用内存检查点与冗余放置降低读取恢复成本。

**评价与边界。** 总恢复时间应从故障发生计到有效训练恢复，而不只从“开始读检查点”计时。也要统计从上一个恢复点到故障之间需要重做的迭代。内存检查点访问快，但与持久化存储的故障域不同，不能假定整批机器掉电后仍可恢复。依据：[SWIFT](../4b_检查点_训练恢复/SWIFT.pdf)、[Gemini](../4b_检查点_训练恢复/Gemini.pdf)、[InMemoryHP](../4b_检查点_训练恢复/InMemoryHP.pdf)。

### 4b.5 热备节点替换

**是什么。** 预先准备备用资源，使故障发生后不必从零申请、加载和初始化。冷备只保留容量或镜像；温备可能已经启动进程或加载部分状态；热备通常更接近可立即接替的状态。术语没有跨系统统一的状态清单，因此报告要明确“备到哪一步”。

**需要准备什么。** 模型/运行时、相容的设备资源、通信连接以及足够新的训练状态。只有加载了模型权重但没有优化器和一致训练步状态，不能完整接替训练rank。备用机器若处在与主机相同的故障域，也可能一起失效。

**减少接替停顿。** 一部分初始化可以提前完成，但真实训练角色可能要等故障发生后才知道。TrainMover研究通过独立准备、影子迭代及通信组设置减少加入时开销；其价值在于让准备工作与现有训练重叠，而不是让备机凭空拥有所有最新状态。接替时仍需满足该系统的状态与通信一致性条件。

**权衡。** 备用GPU长期占用会降低常态资源利用率；共享备用池节省容量，但多个作业同时故障时可能不够用。评价应同时给出接替时间、备用资源比例、状态复制开销、多故障覆盖范围和整体有效训练产出。依据：[TrainMover](../4b_检查点_训练恢复/TrainMover.pdf)、[TPUResiliency](../4a_监控_故障诊断/TPUResiliency.pdf)、[Gemini](../4b_检查点_训练恢复/Gemini.pdf)。

### 4b.6 变规模训练与弹性恢复

**是什么。** 训练资源数量发生变化后，重新分配模型、数据与执行计划，使作业继续运行。例如节点失效后用更少设备续训，或新资源到来后扩大规模。它与只把失败节点换成同配置节点不同，可能改变并行拓扑与每张卡承担的工作。

**系统层需要改变。** 重建通信组、重新分片参数与优化器状态、调整流水线阶段和数据分配，并确保新布局显存够用。Oobleck用不同节点数量的流水线模板和副本冗余支持恢复；ReCycle讨论流水线适配；ByteCheckpoint支持状态重分片所需的基础能力。通用弹性启动工具本身不负责保证任意模型都能在任意卡数上运行。

**训练语义也要检查。** 简化全局批量为`B_global = B_micro × D × A`，D为数据并行度，A为梯度累积次数。若D减半而其他不变，全局批量也减半；可以增加A维持批量，但每次更新的耗时会改变。学习率计划、样本重复/遗漏、随机数序列及总训练步的含义也要保持一致或明确重新定义。

**评价。** 记录重新配置时间、恢复后吞吐、质量变化、数据处理一致性和新增资源利用率。逐位可复现与统计意义上的训练质量一致是两个不同要求，变化的并行归约顺序可能导致细微数值差异。依据：[Oobleck](../4b_检查点_训练恢复/Oobleck.pdf)、[ReCycle](../4b_检查点_训练恢复/ReCycle.pdf)、[ByteCheckpoint](../4b_检查点_训练恢复/ByteCheckpoint.pdf)、[PyTorch Elastic](https://docs.pytorch.org/docs/stable/elastic/run.html)。

### 训练恢复的统一评价口径

`故障总损失 = 检测与决策时间 + 重启/重配置时间 + 状态恢复时间 + 重做计算时间 + 恢复后的性能损失`

这些项在某些系统中可以重叠，不能在测量时重复计数。建议同时报告常态检查点开销与故障后的损失，给出故障类型、注入位置和次数。只展示“最快一次恢复”无法充分说明长期有效训练时间。

## 4c 在线推理高可用与SLO保障

训练故障通常允许回滚并重算；在线推理直接面对用户，除了是否成功，还要考虑首token等待、输出停顿和已经发送的内容。模型权重相同不等于请求状态相同，服务副本恢复也不自动意味着会话能从断点继续。

### 4c.1 高可用、SLO与有效吞吐

**概念区别。** 高可用关注服务能否持续提供功能；SLI是可测量的指标；SLO是对指标的目标；SLA通常还包含对外协议和责任。一个接口始终返回响应，但响应经常超时，可能功能上可达却不能满足服务目标。

**LLM应看哪些指标。** 请求成功率、TTFT、TPOT、相邻token间隔及端到端完成时间。流式场景中平均TPOT可能很好，但中途突然停顿数秒，用户仍会感觉卡顿。不同任务的SLO也不同：交互助手、长文档分析和离线生成不应默认同一延迟门槛。

**Goodput。** 常见请求级定义为`goodput = 测量窗口内满足规定SLO且完成的请求数 / 窗口长度`。也有token级或其他口径，必须明确。假设系统A每秒完成100个请求，其中60个满足全部目标；B完成90个，其中85个满足目标，在这一请求级口径下B的goodput更高。

**统计陷阱。** 不能只在成功请求上算延迟，却完全隐藏被拒绝或失败的请求，否则大量拒绝也能制造漂亮尾延迟。应同时报告到达率、接纳率、拒绝率、成功率和符合SLO的产出；按业务类别分组，避免低优先级请求被平均数淹没。依据：[SLOMetrics](../4c_推理高可用_SLO/SLOMetrics.pdf)、[SCORPIO](../4c_推理高可用_SLO/SCORPIO.pdf)、[JITServe](../4c_推理高可用_SLO/JITServe.pdf)。

### 4c.2 实例故障转移

**是什么。** 当前推理实例无法继续提供服务时，将后续工作交给健康实例。常见流程是检测失联、从路由中移除故障实例、选择目标、恢复或重建状态，再继续执行。检测太慢会延长中断，过于激进则可能把短暂拥塞误判为故障。

**新请求与运行中请求不同。** 新请求通常只需路由到其他已加载模型的实例；运行中请求还包含输入、已生成token、采样设置、KV、位置和流式输出进度。若只部署多个模型副本，故障后可能仍需要把在途请求从头算起。

**流式语义。** 已发送给用户的token无法简单撤回。恢复端应知道输出已确认到哪里，避免重复发送，也要避免丢掉尚未确认的部分。若应用要求故障前后严格延续，还需定义请求ID、token序号、随机状态和状态版本。这是系统设计要求，不是普通负载均衡器自动提供的保证。

**评价。** 检测到恢复输出的中断时长、丢失/重复token、请求完成率、冗余资源和故障期间的goodput。Ray Serve的副本和控制层容错是服务基础，LLM状态续接仍需额外设计。依据：[DejaVu](../4c_推理高可用_SLO/DejaVu.pdf)、[Ray Serve容错文档](../官方工程文档/RayServe_FaultTolerance.html)。

### 4c.3 KV状态迁移

**为什么迁移。** 活实例可能需要缩容、维护或负载均衡，但其中已有请求尚未结束。迁移将请求执行权及必要状态转移到另一实例。LLM权重常已在目标存在，最主要的每请求状态是KV，外加token、位置和采样等元信息。

**常见过程。** 简单做法是暂停、完整复制KV、在目标恢复；停顿随状态大小增长。更复杂的活迁移可以先复制不再变化的历史块，源端继续生成，最后短暂停顿同步新增部分并交接执行权。交接要防止两个实例同时输出同一请求，必要时使用版本或所有权机制。

**适用边界。** Llumnix利用活迁移进行请求重调度，这依赖源实例仍可参与复制。若源GPU突然丢失且没有状态副本，不能再使用同一活迁移路径取回KV。网络带宽低、目标空间不足、分片布局不兼容时，迁移可能不划算。

**怎么评价。** 迁移字节数、总迁移完成时间、用户可见停顿、对源/目标其他请求的影响，以及迁移后是否真正改善负载。总迁移过程很长但停顿很短是可能的，二者应分开报告。依据：[Llumnix](../4c_推理高可用_SLO/Llumnix.pdf)、[DistServe](../3b_大模型推理加速/DistServe.pdf)。

### 4c.4 KV状态重建与复制恢复

**没有KV时怎么办。** 如果保留了完整输入和已生成token，目标可以对这段已知序列重新前向，构建其KV，再从后续位置继续。这是重放已知token，不是重新采样出一段“差不多”的文本。对于确定的模型与注意力配置，重算可得到对应状态，但精度、执行顺序和模型版本差异仍需控制。

**迁移与重建的取舍。** ServerlessLLM研究传输token并在目标重算KV，以减少迁移网络流量。令待传KV大小为M、有效带宽为B，传输时间下界约M/B；若重算前缀所需时间为T_recompute，可在考虑目标负载和并行度后比较两者。较长上下文通常使两种成本都增加，并非永远有一个方案占优。

**复制恢复。** DejaVu通过流式保存/复制KV降低故障后的状态损失。更频繁复制可以减少需重做的部分，但增加带宽和存储开销；最新生成的token可能尚未复制完成，需要明确恢复点。副本放在同一故障域会削弱保护效果。

**必要元数据。** 除token和KV，还要考虑模型/适配器版本、位置编码配置、采样参数、输出确认进度，严格续接时还可能需要随机数状态。MoE或特殊混合架构还应按其实际请求状态设计，不能假定所有模型只需标准KV。

**评价。** KV复制开销、重算token量、恢复时间、状态完整性和故障后的结果一致性。依据：[ServerlessLLM](../4c_推理高可用_SLO/ServerlessLLM.pdf)、[DejaVu](../4c_推理高可用_SLO/DejaVu.pdf)；前沿延伸：[GhostServe](../4c_推理高可用_SLO/GhostServe.pdf)、[LUMEN](../4c_推理高可用_SLO/LUMEN.pdf)。

### 4c.5 请求重调度

**是什么。** 在请求首次进入系统之后，根据实时负载、状态位置与截止时间重新决定在哪里、何时执行。最短队列并不一定是最佳目标：某实例队列短，却没有共享前缀、剩余显存少或正在处理很长Prefill。

**需要考虑的信息。** 请求当前阶段、已有KV位置、估计剩余输出长度、SLO剩余预算、目标计算/显存压力、迁移成本和缓存命中。估计会有误差，因此调度器应留出裕度，避免把很紧的SLO建立在过于精确的长度预测上。

**具体例子。** 一个短交互请求排在长Prefill之后，迁到另一个已加载模型的实例可能改善首token延迟；一个拥有很长KV且即将结束的请求，迁移成本可能大于剩余执行时间，保留原地反而更合理。要比较的是完成请求的总成本，不只是队列人数。

**稳定性。** 若根据瞬时指标频繁迁移，请求可能在实例间来回移动，增加通信并降低缓存命中。可设置最小收益阈值、迁移冷却时间或批量决策。这里是综合工程建议；Llumnix提供请求重调度实例，SCORPIO与JITServe可用于进一步比较SLO感知策略。

**评价。** 分业务goodput、尾延迟、迁移次数、迁移流量、公平性及长请求饥饿情况。依据：[Llumnix](../4c_推理高可用_SLO/Llumnix.pdf)、[SCORPIO](../4c_推理高可用_SLO/SCORPIO.pdf)、[JITServe](../4c_推理高可用_SLO/JITServe.pdf)。

### 4c.6 过载保护

**为什么不能无限排队。** 当长期到达工作量超过系统处理能力，排队时间会不断增长。LLM请求还会占用不同数量的KV和计算，仅限制请求数可能无法约束实际负载。过载时所有请求都接收，最终可能大多数超时，甚至触发内存耗尽。

**主要机制。** 入口限流、按token或估计工作量做准入、限制等待队列、设置超时与取消、为重要业务预留资源，并及时拒绝已经不可能完成的工作。Little定律`L = λW`在稳定系统和一致统计口径下连接平均在系统数量、吞吐与逗留时间；它帮助理解排队代价，但不是突发过载下的瞬时精确预测公式。

**为何重试可能更糟。** 超时客户端若立即同时重试，会把一次过载放大为重试风暴。需要限定重试次数、加入退避和抖动，处理取消传播，并区分已完成但响应丢失与真正未执行。具体重试语义应与请求幂等性和应用行为一致。

**与扩容的关系。** 扩容需要启动、加载和预热，通常不是瞬间生效。过载保护负责在这段时间内守住队列和状态上限；扩容解决持续容量不足，两者不能互相替代。故障也会突然降低有效容量，因此保护策略应能响应容量变化。

**怎么评价。** offered load（到达负载）、接纳率、拒绝率、超时率、排队长度和已接纳请求SLO，并展示负载超过容量之后系统是否平稳。依据：[Ray Serve生产实践](../官方工程文档/RayServe_LoadShedding.html)、[SCORPIO](../4c_推理高可用_SLO/SCORPIO.pdf)、[KunServe](../4c_推理高可用_SLO/KunServe.pdf)。

### 4c.7 服务降级

**是什么。** 容量不足或局部故障时，以事先定义的方式降低服务成本或延后完成，从而保留关键能力。常见可选策略包括降低并发服务级别、转异步处理、限制可选输出长度、使用经过验证的较小模型或关闭非必要步骤。不同策略对内容质量和用户体验影响不同。

**与拒绝的区别。** 负载削减可以直接拒绝请求；降级通常仍提供某种服务。减少最大生成长度可能截断答案，更换小模型会改变能力，压缩输入可能遗漏关键信息。这些变化需要由产品或业务事先定义可接受范围，不能把任意削减都包装成“无损优化”。

**状态与缓存问题。** 更换模型后，原模型的KV一般不能直接作为新模型的KV继续使用；需要重建状态或重新开始相应处理。因此降级策略最好在准入时决定，或明确处理中途切换的代价与输出规则。多级模型的路由也要独立验证任务质量。

**评价框架。** 同时记录服务成本、成功率、延迟和任务质量，建立“负载升高时的质量—时延曲线”。关键业务可选择保留高质量并排队，普通业务可接受快速低成本结果；具体优先级属于业务策略。此节是基于SLO与生产服务机制的综合设计建议，不声称所有所引系统实现了这些降级方式。

**阅读依据。** [SLOMetrics](../4c_推理高可用_SLO/SLOMetrics.pdf)用于指标与用户体验；[SCORPIO](../4c_推理高可用_SLO/SCORPIO.pdf)用于异质目标；[Ray Serve生产实践](../官方工程文档/RayServe_LoadShedding.html)用于服务侧保护。

### 故障后的系统联动示例

某Decode实例故障后，首先移除该实例的路由并确认受影响请求；有有效KV副本的请求从副本恢复，只有token记录的请求重建KV；调度器按目标余量分配请求，同时收紧新请求准入，避免恢复流量挤垮健康实例。备用实例预热完成后恢复容量，再逐步解除限制。评价这一流程时，应包含受影响请求与未故障请求的尾延迟，而不只测量恢复实例自身的速度。

## 术语、公式与横向比较

### 术语速查

| 术语 | 中文含义 | 阅读时要分清 |
|---|---|---|
| AMP | 自动混合精度 | 自动选择部分运算精度，不代表所有状态低精度 |
| PTQ / QAT | 训练后量化 / 量化感知训练 | 校准与训练成本不同 |
| W4A16 / W8A8 | 权重/激活位宽记号 | 不自动包含KV和累加器格式 |
| GEMM | 通用矩阵乘 | 内核速度与模型端到端速度不同 |
| HBM | GPU高带宽显存 | 与寄存器、共享内存的层级不同 |
| IO-aware | 考虑数据移动的算法设计 | 减少访存不等于同幅度减少算术运算 |
| Prefill | 输入上下文前向计算 | 通常产生用于首输出token的分布及输入KV |
| Decode | 自回归增量生成 | 每步读取历史状态并追加状态 |
| KV Cache | 各层键值状态缓存 | 与模型权重、响应文本缓存不同 |
| GQA / MQA | 分组查询/多查询注意力 | KV头数可能少于查询头数 |
| TTFT | 首token延迟 | 需明确是否包含入口、排队和网络 |
| TPOT | 每输出token的平均时间 | 平均值可能掩盖长停顿，且分母口径需说明 |
| ITL / TBT | 相邻token间隔 | 适合描述流式输出的抖动 |
| SLI / SLO | 服务指标 / 服务目标 | 测量值与目标约束不是一回事 |
| Goodput | 符合规定目标的有效处理量 | 请求级与token级定义不能混用 |
| NFE | 函数或网络评估次数 | 不一定等于采样器的步数 |
| Surrogate | 代理模型 | 近似解要与参考求解器按误差标准比较 |
| Straggler | 落后者 | 是相对进度慢的表现，不必然是硬件坏了 |
| Gray failure | 灰故障 | 功能可用但性能或可靠性已退化 |
| SDC | 静默数据损坏 | 可能没有进程崩溃或明显速度下降 |
| Checkpoint | 检查点 | 能续训的状态通常多于模型权重 |
| Staging | 快照暂存/状态搬运 | 暂存完成与远端持久化完成不同 |
| Resharding | 状态重分片 | 文件重新分配不一定等价于张量重组 |
| RTO / RPO | 恢复时间目标 / 恢复点目标 | 目标值与实测恢复时间、实际数据损失不同 |
| Backpressure | 背压 | 下游来不及消费时约束上游生产 |
| Load shedding | 负载削减 | 可以拒绝部分工作，不能隐藏拒绝率 |

### 关键公式及适用前提

| 简化关系 | 变量与意义 | 不能忽略的边界 |
|---|---|---|
| `权重字节数 ≈ 参数量 × 位宽 / 8` | 理想原始存储 | 不含尺度、未量化部分和工作区 |
| `KV字节数 ≈ 2LTH_kvdb` | L层、T个token、KV头数H_kv、头维d、b字节 | 分片、复制、滑动窗口、分页对齐会改变实际值 |
| `传输时间 ≥ 状态字节数 / 有效带宽` | 不含额外处理的下界 | 实际还受排队、同步与布局转换影响 |
| `调优回本调用数 ≈ 调优时间 / 单次节省时间` | 简单时间摊销 | 不含成本差异，且节省时间必须为正 |
| `保存与重做损失率 ≈ C/τ + λτ/2` | 保存成本C、间隔τ、故障率λ | 需要近似独立故障及较小开销，忽略其他恢复项 |
| `τ ≈ √(2C/λ)` | 上述简化目标的极小点 | 不是可直接部署的通用最佳保存周期 |
| `B_global = B_micro × D × A` | 微批量、数据并行度、累积次数 | 假定各数据并行副本微批一致 |
| `L = λW` | 稳态平均在系统量、吞吐、逗留时间 | 不是不稳定队列的瞬时公式；此λ与故障率符号同形但含义不同 |
| `请求goodput = 符合全部指定SLO的完成数 / 时间` | 有效服务产出 | 同时报接纳、拒绝与失败情况 |

### 最容易混淆的九组概念

| 概念对 | 核心差别 |
|---|---|
| 混合精度 vs 推理量化 | 前者围绕训练计算与状态数值稳定性；后者围绕部署表示及推理成本，可有技术交叉 |
| FlashAttention vs PagedAttention | 前者主要优化注意力IO与执行；后者结合分页KV内存管理与注意力访问 |
| 前缀缓存 vs Diffusion跨步缓存 | 前者复用相同前缀计算；后者通常近似复用不同时间步的相似结果 |
| 连续批处理 vs PD分离 | 前者改变执行成员调度；后者改变阶段资源部署 |
| 推测解码 vs 蒸馏少步Diffusion | 前者用候选与验证减少串行目标调用；后者训练学生压缩生成轨迹 |
| 慢链路 vs 最晚进入通信的rank | 网络执行慢与上游迟到都可造成通信等待，需要分辨 |
| 异步保存 vs 持久化完成 | 训练恢复运行不表示最新快照已具备承诺的故障保护 |
| 活迁移 vs 崩溃恢复 | 前者源端通常仍可协助；后者必须依赖幸存状态、复制或重建 |
| 吞吐 vs Goodput | 完成更多工作不保证更多工作符合延迟和质量目标 |

### 建议采用的报告评价模板

每项技术按“具体瓶颈 → 机制 → 成本转移 → 适用条件 → 对照实验 → 局限”组织。对照实验固定模型版本、质量门槛、输入输出分布、并发、硬件及软件配置。训练看达到目标质量的总时间；推理看SLO下有效产出；科学计算看达到科学目标的总时间与误差；可靠性看常态开销和故障损失之和。
