# 6.3 计算与模型执行优化

计算与模型执行优化是提升智算集群有效算力利用率的重要环节。在资源配置与并行策略确定后，模型性能仍受数值表示、算子实现、内存访问和运行时调度等因素影响。大语言模型的预填充与解码具有不同的计算和访存特征，扩散模型需要多次执行去噪网络，HPC-AI 应用还涉及仿真、训练与推理之间的数据交换。因此，执行优化既要降低单个设备上的计算与访存开销，也要考察这些改进能否减少模型切分、跨卡通信和阶段等待，最终提高整个集群的有效吞吐。本节分别讨论低精度计算、算子与编译、大模型推理、扩散模型和 HPC-AI 工作流优化。

## 6.3.1 混合精度训练与推理量化

低精度计算通过缩短权重、激活和梯度的表示位宽，减少显存占用与数据搬运，并利用加速器的低精度矩阵单元提高吞吐。对智算集群而言，显存节省还可能使模型采用更少的张量并行或流水线并行分片，从而缩小通信域、减少同步次数，并释放更多设备承载其他作业；若维持原并行规模，则可用于扩大批量或序列长度。不过，数值范围和舍入误差会影响长周期训练的收敛，因此低精度优化的核心不是统一降低所有张量的位宽，而是根据张量用途保留必要的计算精度。

Mixed Precision Training 确立了 FP16 混合精度训练的基本方法：前向和反向的主体计算使用 FP16，参数更新保留 FP32 主权重，点积与归约采用较高精度累加，并通过损失缩放避免小梯度下溢。BF16 保留了与 FP32 相同的指数范围，通常降低了损失缩放的管理难度，但关键归约和优化器状态仍需谨慎处理。进入 FP8 阶段后，训练需要在 E4M3 的有效精度和 E5M2 的动态范围之间选择，并配合张量缩放和离群值控制。Scaling FP8 Training to Trillion-Token LLMs 在 256 个 Gaudi2 上完成 7B 模型的万亿 token 级训练，说明 FP8 已能用于长程训练，但其稳定性依赖对 SwiGLU 离群值和优化器状态的专门处理；COAT 进一步量化激活与优化器状态，在 Llama 7B—30B 的测试中相对 BF16 将端到端显存占用降低约 1.54 倍、训练速度提高约 1.43 倍。随着单卡计算时间缩短，集合通信和数据供给在迭代时间中的占比会相应上升，因此集群侧还需同步调整通信重叠和数据管线。

推理量化需要根据服务瓶颈选择权重、输入激活和 KV Cache 等对象。GPTQ 与 AWQ 均以权重量化为主，分别通过近似二阶误差补偿和重要通道保护降低低比特误差，适合权重读取占比较高的解码阶段。SmoothQuant 通过通道缩放把激活离群值的量化难度转移到权重侧，使权重和激活均可采用 INT8；QServe 则进一步采用 W4A8KV4，并把反量化与 INT8 矩阵计算结合。量化后的模型如果能够从多卡缩减到单卡或单节点部署，收益将同时体现在显存容量、跨卡同步和副本调度上；对于长上下文服务，压缩 KV Cache 还可提高单个副本的并发数，减少因显存不足引起的排队和扩容。

低精度能否转化为集群有效算力，取决于模型质量、访存瓶颈、类型转换开销、内核覆盖率和并行布局。训练侧通常保留 FP32 主权重与关键累加路径，推理侧则应根据预填充、解码和上下文长度选择压缩对象。比较不同方案时，需要固定模型、硬件、后端、批大小及输入输出长度，同时报告模型质量、单卡性能和集群扩展效率，不能把理论压缩比或单算子加速直接视为端到端收益。

## 6.3.2 算子、内核与编译优化

低精度表示只有落到合适的内核上才能形成加速。神经网络中的逐元素运算计算量较小，却会频繁启动内核并反复读写中间张量；注意力等复杂算子还受片上存储、显存带宽和并行划分影响。图级重写首先需要在保持模型语义不变的前提下寻找更优执行图，TASO 为此自动生成并验证等价变换。但是，图结构可行并不代表底层内核一定高效，Apollo 进一步把图分区与算子内部循环优化联合起来，Welder 则按数据块估算内存流量，在算子内外的数据复用中选择执行计划。这一演进使优化目标从减少算子数量逐步转向减少真实的数据搬运，从而提高设备用于有效计算的时间比例。

算子融合的收益存在明确边界。融合后的内核通常占用更多寄存器和共享内存，可能降低并发驻留的线程块数量；对已经接近计算峰值的矩阵乘，继续扩大融合范围也未必有效。在单卡上，这表现为吞吐不再随融合深度提高；在集群中，计算内核变快还会缩短通信可被隐藏的时间，使原先不明显的集合通信或流水线气泡成为新瓶颈。因此，融合粒度需要结合张量形状、硬件资源和并行策略确定，评价时也应区分算子时间下降与整个训练迭代时间下降。

注意力内核集中体现了这种关系。标准注意力需要生成与序列长度平方相关的中间矩阵，若将其完整写回显存，会产生较高的访存开销。FlashAttention 把 Q、K、V 分块载入片上存储，通过在线 softmax 逐块更新结果，避免完整注意力矩阵落入显存；FlashAttention-2 进一步调整线程块和 warp 分工，在 A100 上达到理论峰值吞吐的 50%—73%，FlashAttention-3 则利用 Hopper 的异步执行与 TMA 加强计算和数据搬运的重叠。对集群训练而言，内核节省的显存可用于增加微批量和序列长度，从而提高计算通信比，但更长序列也会增加激活和并行通信，因此仍需与张量并行、序列并行共同配置。服务侧的形状又不同：FlashInfer 面向动态序列和分块 KV Cache 提供可组合模板，FlashDecoding++ 通过异步 softmax、双缓冲和数据流选择改善单步解码，说明训练、预填充与解码不能共享一套固定内核方案。

编译系统负责把图变换、融合和硬件选择转化为可重复执行的计划。TVM 将图级优化、算子调度和学习型成本模型结合，建立了跨硬件生成高效代码的基本路径；Ansor 又通过自动构造搜索空间，减少了对人工调度模板的依赖。随后，TensorIR 增强了编译表示对硬件张量原语的表达能力，PyTorch 2 则把动态图捕获与内核生成接入常用训练框架，使上述优化更容易进入实际模型。对于大规模集群，编译结果还需在大量设备和进程间保持一致，并适应硬件代际、输入形状和并行配置的变化；频繁重新编译会增加作业启动和弹性恢复时间，过度依赖特定硬件内核也会降低异构资源的可调度性。因此，评价除端到端时延外，还应包括显存读写量、硬件占用率、编译缓存命中率和启动时间，并观察算子优化后通信在总时长中的占比变化。

## 6.3.3 大模型推理执行优化

大模型推理分为预填充和解码两个阶段。预填充一次处理完整输入，计算密度较高；解码逐 token 生成结果，需要持续读取模型参数和 KV Cache，通常受访存限制。两类请求共用设备时，较长的预填充会阻塞解码并抬高尾时延，而静态批处理又会因请求长度不同造成资源空转。Orca 通过迭代级调度实现连续批处理，使请求能够在解码步之间动态进入和退出批次；Sarathi-Serve 进一步把长预填充拆成小块，与解码交错执行。它们的共同作用是提高单个推理副本的利用率，但在集群层面仍需根据请求长度和 SLO 分配流量，否则局部形成的大批次可能转化为更高的排队和 KV Cache 压力。

KV Cache 管理决定了每个副本可承载的并发规模，也影响集群需要部署多少模型副本。PagedAttention 借鉴分页机制，将 KV Cache 划分为固定大小的块并按需映射，减少连续预留产生的碎片；基于该机制的 vLLM 在相同延迟水平下相对当时系统报告了 2—4 倍吞吐提升。多轮对话、检索增强生成和智能体应用还会产生大量重复前缀，SGLang 以基数树组织缓存，Prompt Cache 则显式定义可复用的提示模块，使共享前缀无需重复执行预填充。这两类技术分别减少容量浪费和重复计算，但会提高缓存元数据与命中管理的复杂度；当缓存扩展到 CPU 内存或 SSD 时，还需比较读取时间与重新计算成本。

当单机显存无法容纳不断增长的状态时，优化范围会从副本内部扩展到集群。Mooncake 把 GPU、CPU 内存和 SSD 组织成分层 KV Cache，并将预填充与解码部署到不同资源池；DistServe 则依据 TTFT 和 TPOT 目标分别配置两个阶段的并行策略和设备。分离部署可以使计算型资源承担预填充、带宽型资源承担解码，但必须在两个资源池之间传输 KV 状态，互联带宽不足时会抵消分离收益。因而，集群调度器需要把请求路由、KV 所在位置和设备负载共同考虑，而不能只按空闲 GPU 数量分配请求。

投机解码从另一方向减少解码的串行步数：先由小模型或附加结构生成候选 token，再由目标模型并行验证。投机解码给出了保持目标分布不变的基本方法，SpecInfer、EAGLE 和 Medusa 分别通过候选树、特征预测和多解码头提高候选质量。其收益取决于候选接受率、草稿计算和验证批量，并会受模型部署位置影响；若草稿模型额外占用一组设备或引入跨节点传输，单请求加速未必能提高集群 goodput。大模型推理因此需要在统一的模型、输入输出长度、并发和 SLO 下，联合评价批处理、缓存、分离部署与投机解码，而不能把各项加速比直接叠加。

## 6.3.4 Diffusion 模型执行优化

扩散模型通过多次调用去噪网络逐步生成样本，总开销近似由采样步数和单步成本共同决定。DDIM 通过改变反向过程显著减少采样步骤，DPM-Solver 把采样视为扩散常微分方程的数值求解，可在约 10—20 次函数评估内获得较高质量，UniPC 又以统一的预测—校正框架改善极少步采样。渐进蒸馏和一致性模型则通过额外训练把生成过程压缩到少数步骤。前一类方法可以直接作用于已有模型，后一类方法推理成本更低但需要重新训练；对集群服务而言，两者都会减少一次请求占用 GPU 的时间，从而提高副本周转率，但也必须在相同生成质量下比较。

当采样步数无法继续下降时，可以利用相邻去噪步之间的时间冗余减少单步计算。DeepCache 复用 U-Net 的高层特征，在 Stable Diffusion v1.5 上报告约 2.3 倍加速且 CLIP 分数仅小幅下降；Learning-to-Cache 把缓存决策细化到 Transformer 层，TeaCache 则根据时间步之间的变化决定视频扩散模型是否复用特征。缓存减少了算力需求，却增加了中间状态的驻留时间和显存占用。在多任务集群中，较大的特征缓存可能压低单卡并发数，因此运行时需要根据请求分辨率、剩余显存和质量要求决定缓存范围，而不能只追求单请求时延。

高分辨率图像和视频生成还可能超过单卡显存或时延上限，需要多 GPU 并行。DistriFusion 把图像切分为多个区域，并复用上一时间步的特征补充跨区域上下文，使通信与计算重叠；在 Stable Diffusion XL 上使用 8 张 A100 时相对单卡报告最高 6.1 倍加速。PipeFusion 进一步结合区域切分与模型层流水，以降低大型扩散 Transformer 的显存和通信压力。此类方案把单请求时延降下来，却占用更多设备并引入跨卡数据交换，只有在高分辨率任务或严格时延目标下才可能优于增加独立副本；集群调度器需要在请求并行和模型并行之间动态选择。

采样器、蒸馏、缓存和多卡并行分别作用于迭代次数、单步计算和资源分配，但其中部分收益来自相同的时间冗余，不能简单相乘。实际评价需要固定模型、分辨率、采样步数和引导尺度，并同时报告函数评估次数与生成质量。在此基础上，再比较单请求时延、设备占用时间和多卡扩展效率，才能判断优化提高的是局部速度还是集群有效吞吐。

## 6.3.5 HPC-AI 代理计算与混合工作流

HPC-AI 场景同时包含数值仿真和机器学习，优化对象从单次模型执行扩展到跨阶段工作流。神经算子学习函数到函数的映射，使一个模型能够在一组参数和边界条件上复用训练结果。DeepONet 用两个网络分别编码输入函数和输出位置，给出了较通用的算子学习结构；Fourier Neural Operator 则在频域表示积分核，以更低的计算成本处理多类偏微分方程和不同空间分辨率。两者都试图用一次训练减少后续的参数扫描和数值迭代，但精度仍取决于训练数据覆盖范围，分布外条件还需传统求解器校验。因此，代理模型在集群中的主要价值是缩短高成本仿真节点的占用时间，而不是完全替代数值计算。

GraphCast 展示了这一模式在真实科学任务中的规模：其全球 0.25° 分辨率的 10 天天气预报可在一分钟内完成，并在多数验证目标上优于当时的业务确定性系统。传统数值天气预报需要持续占用大型 CPU 集群，代理模型则把计算转移到较短的 GPU 推理阶段，使同一资源预算能够支持更多集合成员或更高的预报频率。不过，训练代理模型本身需要大量历史数据和加速器资源，极端事件与分布变化也要求与观测及物理模型交叉验证。因而，集群规划应同时计算模型训练投入、日常推理节省和回退到数值求解的成本。

另一条路线把 AI 推理放回仿真闭环，用模型结果决定下一步计算。SmartSim 支持仿真程序在运行中调用分布式模型，使数据通过内存服务而非文件系统交换；DeepDriveMD 利用在线模型筛选更有价值的分子动力学轨迹，把算力集中到更可能产生科学结果的区域。对于包含仿真、训练和推理的多阶段任务，Colmena 通过事件驱动工作流和动态调度减少阶段等待。三者反映的共同问题是资源异构：仿真可能主要使用 CPU，模型训练和推理依赖 GPU，阶段之间还需传输大量中间数据。若调度器不能同时处理资源配额和数据位置，某一阶段的加速会转化为下一阶段的排队。

HPC-AI 工作流需要同时采用系统指标与科学指标。系统侧包括 CPU 和 GPU 利用率、排队与空闲时间、数据搬移量、扩展效率和总求解时间；科学侧包括误差、有效样本、收敛速度或发现数量。代理模型降低单次求解成本，在线闭环改变计算顺序，工作流调度决定资源能否持续利用，三者共同影响最终产出。只有在相同误差门槛和算力预算下比较单位时间获得的科学结果，才能判断混合工作流是否真正提高了智算集群的有效算力。

# 6.4 大规模集群可靠性与容错

随着智算集群从千卡扩展到万卡乃至更大的资源池，可靠性问题会由偶发的部件故障转变为影响作业效率的常态因素。同步训练把大量设备、网络链路和存储节点连接成一条执行链，其中任一环节退出或变慢，都可能造成全局等待、检查点回滚和算力空转；在线推理还需在故障期间维持请求处理和服务等级。因此，集群可靠性不能只用设备是否在线衡量，而应形成“监测—诊断—隔离—状态保存—恢复”的闭环，并以有效训练时间、作业 goodput 和服务 SLO 评价实际收益。

## 6.4.1 集群故障特征与可观测性

大规模训练故障首先表现为作业层故障频率随参与设备和运行时间增加。MegaScale 与 Tessera 均将单个训练作业扩展到 12,288 张 GPU，Google Cloud 的公开测试进一步跨 199 个 Pod 使用 50,944 个 TPU v5e 芯片。即使单个部件具有较高可靠性，设备、网卡、交换链路和软件进程的大量组合，也会缩短作业两次异常之间的间隔。训练持续时间越长，遇到至少一次故障的可能性越高，可靠性问题因而从偶发事件转变为长周期训练必须持续处理的运行状态。

其次，故障具有跨层耦合和同步放大的特征。同一次迭代停顿可能源于 GPU 降频或显存错误，也可能来自网卡重传、集合通信失衡、存储阻塞和数据供给不足；这些异常在单个节点上可能只造成轻微延迟，却会通过同步屏障传递给全部参与进程。部分问题还具有间歇性，只在特定通信模式、负载强度或拓扑位置下出现，使离线测试难以稳定复现。因此，集群故障不能只按“节点退出”统计，还应记录性能退化、通信等待和数值异常对有效训练时间的持续影响。

生产资源池的异构性进一步增加了判断难度。ByteRobust 所在平台超过 20 万张 GPU，EROICA 的在线诊断覆盖约 10 万张 GPU，Alibaba ASI 的轨迹则包含 155,410 张不同厂商和代际的 GPU。在这种环境中，不同型号、机架和网络位置本来就具有不同的性能基线，固定阈值容易把正常差异判为故障，也可能漏掉相对同组设备已经明显退化的节点。故障识别需要结合硬件类型、拓扑位置、作业角色和历史表现建立分组基线，并判断异常是否落在当前训练的关键路径上。

上述特征决定了可观测性必须具备跨层、时序关联和低开销三项能力。设备计数器用于发现温度、功耗、显存和链路错误，系统与集合通信时间线用于还原等待的传播路径，训练步骤、损失和梯度统计用于判断异常是否已经影响进度或结果；各层记录还需使用统一时间戳，并与作业放置和网络拓扑关联。EROICA 采用常态低开销采集与异常后细粒度分析相结合的方式，ByteRobust 则把监测结果继续连接到诊断、热修复和恢复。这样，可观测性才不只是汇集指标，而是能够回答故障发生在哪里、如何影响全局以及应当采取何种处置。

## 6.4.2 故障诊断、落后者定位与主动隔离

集群异常可分为进程或节点退出的 fail-stop、持续拖慢执行的 fail-slow，以及不报错却破坏计算结果的静默数据损坏。Fail-stop 通常能够通过心跳和错误日志发现，但进程退出未必就是根因，也可能由网络中断、设备错误或上游服务异常引起；fail-slow 和静默错误则往往没有明确告警。同步训练还会在集合通信处等待全部参与者，使局部异常扩展为全局停顿。因此，故障诊断需要依次完成异常检测、故障分层、组件定位和影响判断，而不能把进程退出位置直接视为故障来源。

落后者定位的难点在于区分正常波动、局部性能退化和真正影响训练进度的关键落后者。GREYHOUND 对超过万卡的生产集群进行在线分析，发现资源争用、设备退化和网络拥塞会形成持续时间不同的落后者，并明显延缓大型训练作业。Mycroft 进一步记录集合通信内部的执行状态，将慢链路、拓扑位置和上层等待关联起来；What-if Analysis 则估计替换某个组件后迭代时间是否会改善。三者形成了从发现步骤变慢、缩小异常通信组，到判断问题组件是否位于关键路径的定位过程，可以避免因非关键波动频繁迁移或重启作业。

静默数据损坏需要从性能诊断转向结果诊断。此类故障通常不会触发进程退出，错误结果还可能被继续传播并写入检查点。SDCs in the Wild 表明，通用压力测试可能遗漏与特定数据和执行单元相关的缺陷，因此采用触发异常的训练负载进行重放，并结合数值校验定位问题设备。生产集群还可在关键算子、梯度统计和检查点写入前设置一致性检查，使结果异常尽量在传播前暴露，并将可疑设备与正常设备进行对照验证。

主动隔离是在故障完全暴露前，根据诊断置信度限制可疑资源的影响范围。对于短时拥塞，可优先调整作业放置、通信路径或数据来源；对于持续退化的设备，可替换对应训练进程并将节点暂时移出资源池；对于可能造成结果错误的设备，则应立即停止其参与计算，并回退到可信检查点。SuperBench 一类健康管理流程可将准入测试、运行监测、异常隔离、维修复测和重新上线连接起来，防止问题节点反复进入作业。评价这一流程时，需要同时考察误报率、漏报率、定位和隔离时间、隔离造成的容量损失，以及作业恢复后的性能变化。

## 6.4.3 分布式检查点与训练状态保存

分布式检查点首先要保证训练状态完整且能够重新组合。除模型参数和优化器状态外，系统还需保存训练步数、随机数状态和数据读取位置，避免恢复后重复或跳过样本。混合并行会把这些状态分散到大量进程，如果检查点只记录当前设备上的物理分片，恢复就会依赖原有 GPU 数量和并行布局。ByteCheckpoint 与 Universal Checkpointing 通过全局元数据和重分片解除这种绑定，使作业能够在不同设备规模或并行配置下恢复。PyTorch Distributed Checkpoint 和 NVIDIA NeMo 也提供了分片并行保存与重新加载能力，说明可移植的分布式格式已经成为大模型训练框架的基础功能。

在多数智算中心，多个训练作业通过共享文件系统或对象存储保存状态，主要瓶颈之一是并发写入占用网络和存储带宽。Check-N-Run 面向数百个生产训练任务、数千张 GPU 和 TB 级推荐模型，指出远端检查点同时受到写带宽、网络带宽和存储容量限制；其差量保存与量化方法将所需写带宽降低 6—17 倍、存储容量降低 2.5—8 倍。这一生产案例说明，检查点优化不仅影响单个作业暂停时间，还关系到多租户环境中共享存储能否承受持续保存流量。

大模型训练进一步放大了单次检查点的数据规模。常用方法可以归纳为三类：PCcheck 将状态复制和持久化移出训练关键路径，DataStates-LLM 与 Gemini 利用主机内存或节点近端存储形成分层保存，LowDiff 则减少相邻检查点的重复内容。Google TPU v5e 的跨 Pod 测试给出了极端规模下的估算：如果 199 个数据并行副本分别从共享存储读取约 1.536 TB 的状态，总读取量将接近 300 TB；改由一个副本读取并通过集群网络广播，可避免相同状态被重复读取。由此可见，并行读写、近端暂存和数据缩减需要根据存储与互联带宽联合选择。

检查点周期应由故障间隔、保存开销和允许回滚的训练量共同决定。保存过少会增加故障后的重复计算，保存过密则可能使网络和存储持续承压；多个作业同时保存还会形成 I/O 峰值，并拖慢同一资源池中的其他任务。平台需要根据作业规模和近期故障水平调整周期，在调度层错开写入，并通过完成标记或版本元数据保证恢复时只读取完整状态。评价时应同时报告训练停顿、后台持久化时间、存储总量、恢复时间和重算步数，把保存与回滚成本一并计入 goodput。

## 6.4.4 故障恢复与弹性训练

故障恢复包括确认影响范围、保留健康进程、申请替代资源、重分片并加载状态，以及重建通信关系。其损失由故障发现时间、资源等待时间、状态恢复时间和回滚计算共同构成。对万卡训练而言，等待与原规模完全一致的健康节点可能比加载检查点更慢；允许作业先以较小规模恢复能够减少停机，却需要重新选择数据、张量和流水线并行布局，并控制规模变化对全局批量和收敛轨迹的影响。

缩小恢复范围可以直接减少状态搬运和重复计算。Gemini 使用主机内存中的近端检查点加快重载，ByteCheckpoint 使替代节点按新布局读取状态；TrainMover 进一步迁移训练角色、状态和通信关系，减少节点替换期间的全局停顿。Oobleck 预先准备逻辑等价的流水线执行计划，ReCycle 则在资源减少后调整流水线继续训练。这些方法都把“整作业重启”改为局部替换或执行重构，但会分别增加主机内存、备用设备、状态迁移流量或并行效率损失。

恢复策略还需要与资源池容量和网络控制联动。ByteRobust 在代表性的 9,600 卡、持续三个月训练中达到 97% 的有效训练时间，依靠的是检测、热修复、备用节点和检查点恢复组成的整体流程，而非单一机制。TPUv4 的实践则说明，一部分芯片和链路故障可先通过互联重配置绕行，减少触发作业级恢复的次数。工程上可根据故障频率保留少量热备资源，资源紧张时先降规模恢复，再在容量到位后扩展；评价则应覆盖停机时间、重算量、备用资源比例、恢复后效率和调度等待时间。

## 6.4.5 在线推理高可用与 SLO 保障

在线推理的可靠性目标与训练不同。副本故障不仅减少服务容量，还会丢失在途请求已经生成的 KV 状态；请求转移到其他副本后又会增加排队，并可能在负载高峰触发级联过载。因此，恢复过程需同时处理模型加载、请求迁移、KV 状态和入口流量，并以首 token 时延、逐 token 时延、尾延迟、SLO 违约率和 goodput 衡量故障期间真正可用的服务能力。

模型参数决定替代实例何时能够接收流量。ServerlessLLM 利用服务器近端存储和内存减少从远端加载模型的时间，BlitzScale 进一步协调快速扩容与参数缓存；SpotServe 则通过细粒度提交推理进度，降低可抢占实例退出造成的重算和尾延迟。集群入口需要在替代实例启动期间限制新请求或将流量转向仍有余量的副本，并保留一定容量缓冲，否则单个副本退出会把压力传给健康节点，使局部故障扩展为服务过载。

KV 状态可采用迁移、复制、纠删码或重新计算。Llumnix 通过跨实例迁移保留已经完成的计算，DéjàVu 以状态流式传输和复制支持恢复，GhostServe 则在主机内存保存校验分片以重建丢失状态。复制恢复快但占用更多内存和带宽，纠删码降低冗余量却增加编码开销，重新执行预填充无需常驻副本但不适合长上下文。调度器应结合上下文长度、状态位置、网络负载和 SLO 选择路径，并在过载时实施准入控制、请求降级或快速扩容。最终配置需将故障期 SLO 收益与长期资源开销放在同一评价框架中。
