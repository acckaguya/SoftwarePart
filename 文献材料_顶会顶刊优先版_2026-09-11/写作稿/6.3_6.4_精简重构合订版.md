# 6.3 计算与模型执行优化

计算与模型执行优化直接影响智算集群的有效算力。在资源配置与并行策略确定后，模型执行仍受数值精度、算子实现、显存访问和运行时调度制约。单卡计算加速还可能暴露通信与数据供给瓶颈，因此需要结合模型特征，将低精度计算、内核优化与集群资源配置共同考虑。本节从底层计算、大模型推理及 Diffusion 与 HPC-AI 应用三个方面展开，以模型质量约束下的端到端吞吐和设备占用衡量优化效果。

## 6.3.1 低精度计算与算子编译优化

低精度计算通过缩短权重、激活和梯度的表示位宽，减少显存占用与数据搬运，并提高矩阵计算吞吐。Mixed Precision Training 采用 FP16 执行主体计算，保留 FP32 主权重和高精度累加，并通过损失缩放避免小梯度下溢；BF16 扩大了相对于 FP16 的数值范围，通常降低了缩放管理难度。FP8 进一步压缩数据，但需要根据张量用途选择格式、缩放粒度和高精度保留位置。Scaling FP8 Training to Trillion-Token LLMs 展示了长周期训练的可行性，也说明数值稳定性仍依赖离群值和优化器状态处理。集群可将节省的显存用于增大微批量或减少模型分片，但计算时间缩短后，还需重新安排通信重叠。

推理量化则应围绕权重、激活和 KV Cache 的实际开销选择对象。GPTQ 通过误差补偿降低权重量化损失，AWQ 保护重要通道，适合权重读取开销较大的解码场景；SmoothQuant 将激活离群值的处理难度转移到权重侧，支持权重与激活同时采用 INT8。对于长上下文服务，KV Cache 压缩还能提高副本并发容量。如果模型因此能够从多节点缩减到单节点部署，收益会同时体现在显存、通信和副本调度上。不过，低位宽只有得到硬件和内核支持，并控制类型转换开销，才能转化为端到端加速。

算子与编译优化进一步减少中间结果的读写和内核启动开销。Welder 按数据块分析算子内外的数据复用，以访存成本指导融合；FlashAttention 将注意力计算分块放入片上存储，通过在线 softmax 避免完整注意力矩阵写回显存。两者均通过减少数据搬运改善执行效率，但融合范围过大会增加寄存器和共享内存占用，反而降低并发。TVM 的自动调优与 PyTorch 2 的图捕获、内核生成将这些优化接入模型执行流程。集群部署还需复用编译结果，并适应输入形状与硬件差异，避免反复编译增加启动和恢复时间。评价时应观察整个迭代的计算、通信和等待变化，确认局部加速是否提高了集群吞吐。

## 6.3.2 大模型推理执行优化

大模型推理的预填充阶段计算密度较高，解码阶段则逐 token 读取参数与 KV Cache，通常更受访存限制。长预填充与解码共用设备时容易形成阻塞，静态批处理又会因请求长度不同造成空转。Orca 以迭代级调度实现连续批处理，使请求动态进入和退出批次；Sarathi-Serve 将长预填充拆分为小块，与解码交错执行。它们提高了设备利用率，但批量扩大也会增加排队和显存压力，因此集群需要根据请求长度及服务等级目标（SLO）共同调整批处理与流量分配。

KV Cache 管理决定单副本容量及集群所需副本数量。PagedAttention 将缓存划分为固定大小的块并按需分配，减少连续预留造成的碎片；SGLang 通过前缀复用减少重复预填充。缓存扩展到多节点后，Mooncake 将 GPU、CPU 内存和 SSD 组织成分层存储，DistServe 则依据首 token 时延与逐 token 时延要求分别配置预填充和解码资源。分离部署有利于分别优化两个阶段，却需要传输 KV 状态。因此，请求路由应同时考虑缓存位置、实例负载和互联带宽，避免计算节省被远端读取与状态迁移抵消。

投机解码通过先生成候选 token、再由目标模型并行验证，减少串行解码次数。其收益取决于候选接受率、草稿生成成本和验证批量；EAGLE 通过特征预测提高候选质量，SpecInfer 则组织候选树以提高验证效率。若草稿模型额外占用设备或增加跨节点通信，单请求加速未必增加集群产出。因此，批处理、缓存、分离部署和投机解码需要联合配置，并在相同模型质量、请求分布和 SLO 下比较有效吞吐，即单位时间内满足服务目标的请求量，而不能直接叠加各项加速比。

## 6.3.3 Diffusion 与 HPC-AI 执行优化

Diffusion 模型需要反复执行去噪网络，总开销由采样步数和单步成本共同决定。DPM-Solver 通过改进数值求解减少采样步骤，渐进蒸馏则通过额外训练将多步生成压缩为少步执行；DeepCache 复用相邻去噪步的高层特征，进一步降低单步计算量。这些方法减少了请求占用 GPU 的时间，但蒸馏增加训练投入，特征缓存也会占用显存。对于高分辨率图像和视频，DistriFusion 与 PipeFusion 通过区域切分、特征复用和流水线并行降低单请求时延。集群需要在多卡处理一个请求和增加独立副本之间选择，并在相同生成质量下比较设备占用时间与总体吞吐。

HPC-AI 的优化范围扩展到仿真、训练和推理之间的工作流。DeepONet 与 Fourier Neural Operator 学习函数之间的映射，通过复用训练结果减少后续数值求解与参数扫描的成本。代理模型可缩短高成本仿真任务的运行时间，但准确性取决于训练数据覆盖范围，分布外条件仍需物理模型校验。因此，其集群收益应同时计入数据生成、模型训练、日常推理和必要的数值回退成本，不能只比较一次推理与一次仿真的耗时。

当 AI 参与仿真过程的实时决策时，瓶颈还会转向跨阶段数据交换与资源等待。SmartSim 支持仿真程序通过内存服务调用模型，DeepDriveMD 利用在线学习筛选后续分子动力学轨迹，将算力用于更有价值的计算。由于仿真、训练和推理的 CPU、GPU 需求不同，调度器需协调资源配额、执行顺序和数据位置，避免一个阶段加速后在下一阶段排队。此类工作流应在相同误差或收敛要求下，评价总求解时间、数据搬移量和资源利用率，将模型执行优化落实到最终科学产出。

# 6.4 大规模集群可靠性与容错

大规模同步训练将大量设备和通信链路连接为一个整体，局部故障可能引起全局等待、作业重启和训练回滚；在线推理还需在实例退出时维持请求处理和服务质量。可靠性建设因此应贯通监测诊断、状态保存与故障恢复，并结合故障造成的停顿、重复计算和容量损失，衡量集群在长期运行中的有效产出。

## 6.4.1 集群故障观测、诊断与隔离

集群故障具有跨层耦合、同步放大和间歇出现的特征。GPU 退化、网卡重传、存储阻塞和数据不足都可能表现为迭代变慢，局部延迟还会通过集合通信扩大为其他进程的等待。MegaScale 的 12,288 卡训练实践说明，稳定运行需要联合观察计算、通信和数据管线；随着作业参与设备及运行时间增加，暴露于异常的机会也随之增多。观测系统应把设备指标、通信时间线和模型数值状态对齐到训练步骤，并结合拓扑与同类设备基线判断异常。EROICA 在约十万卡生产集群中的在线诊断实践，为这类跨层观测提供了直接证据。

诊断需要区分进程退出、性能退化和静默数据损坏，并进一步确定异常组件对全局进度的影响。GREYHOUND 定位万卡生产环境中的落后者，Mycroft 通过集合通信追踪关联慢链路与上层等待，What-if Analysis 则估计替换组件是否真正缩短迭代时间。它们分别帮助发现异常、缩小范围和判断影响，不能将观察到的所有等待进程都视为故障源。对于不触发报错的数值错误，SDCs in the Wild 采用触发异常的真实负载进行重放，说明通用压力测试之外还需要针对训练数据和执行路径的验证。

诊断结果需与调度系统连接，形成隔离和重新准入流程。短时拥塞可先调整放置或通信路径，持续性能退化的设备应在替换后暂时移出资源池，可能破坏结果的设备则需停止参与计算并检查已有状态的可信性。SuperBench 将准入测试、运行监测和维修复测纳入健康管理，减少问题节点反复进入作业。隔离范围应依据故障证据和影响确定：过小会留下隐患，过大则损失可用容量，因此需综合考察误报率、定位时间、隔离资源量和处置后的作业性能。

## 6.4.2 分布式检查点与弹性恢复

检查点是恢复训练进度的基础，需要保存同一训练步骤的参数、优化器、随机数和数据读取状态。混合并行将状态分散到多个设备，ByteCheckpoint 与 Universal Checkpointing 通过元数据映射和重分片，支持在不同资源规模或并行配置下重新加载。保存过程中还应确认分片完整并提交可恢复版本，防止读取尚未完成的状态。这样，检查点既限制了故障后的重复计算，也使调度器能够利用当前健康资源恢复作业，降低对原设备集合的依赖。

共享存储压力决定了检查点能否以足够高的频率保存。Check-N-Run 面向数百个生产任务、数千张 GPU 和 TB 级推荐模型，显示远端检查点同时受到网络、写带宽和容量限制；这一场景说明，状态保存还会影响同一资源池中的其他任务。异步写入可减少训练停顿，Gemini 利用分布式主机内存加快状态保存与恢复，差量保存则减少重复内容，但这些方法分别需要额外缓冲、冗余空间或恢复处理。平台应结合故障间隔和回滚成本确定保存周期，错开并发写入，并区分近端保存完成与远端持久化完成所能承受的故障范围。

恢复效率还取决于资源等待和通信重建。具备替代节点时，可通过迁移训练状态与角色缩短替换过程；资源不足时，Oobleck 与 ReCycle 等系统通过重新组织流水线支持故障后的训练延续。变规模恢复需要协调并行布局、微批量和梯度累积，使全局批量、数据进度与优化器状态保持一致。允许降规模运行能减少等待，但可能降低后续吞吐，因此需比较立即恢复与等待更多资源的总体完成时间，并计入备用节点和迁移带宽的成本。

生产实践表明，上述机制需要作为整体协同工作。ByteRobust 在超过二十万卡的平台上部署，其代表性 9,600 卡长期作业达到 97% 的有效训练时间比例；平台总量与单作业规模应分别理解。TPUv4 则通过互联重配置绕过部分芯片和链路故障，减少对训练作业的干扰。这些案例说明，集群可先在设备和网络层处理可恢复异常，必要时再执行状态回滚与资源重组，并以停机、重算、资源等待和备用容量共同评价恢复收益。

## 6.4.3 在线推理高可用与 SLO 保障

推理副本退出会同时损失服务容量和在途请求状态，请求转移后还可能使健康副本过载。ServerlessLLM 利用近端存储加快模型加载，BlitzScale 协调参数缓存与扩容，缩短替代实例承接流量前的等待。扩容期间，入口需根据剩余容量限制新请求、调整路由并预留一定缓冲，避免一次实例故障扩展为集群级排队。因此，实例启动速度必须与流量控制共同设计，才能转化为故障期间可用的服务能力。

长请求恢复还需处理 KV 状态。Llumnix 支持跨实例迁移以保留已完成计算，DéjàVu 通过状态传输和复制支持恢复，GhostServe 利用主机内存中的校验分片重建丢失状态。主动迁移要求源状态仍可访问，突发故障则依赖预先保存的冗余或重新计算；复制消耗内存和带宽，纠删码增加恢复计算，重新预填充的成本随上下文增长。调度器应结合状态位置、请求长度和网络负载选择方式，并在容量不足时实施准入控制或服务降级。评价需覆盖稳态、过载和故障期间的首 token 时延、逐 token 时延、SLO 违约率及有效吞吐，同时计入状态冗余与备用容量的长期成本。
