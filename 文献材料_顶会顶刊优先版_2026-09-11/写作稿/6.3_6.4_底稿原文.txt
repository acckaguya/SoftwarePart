6.3 计算与模型执行优化
计算与模型执行优化是提升智算集群有效算力利用率的重要环节。在资源配置与并行策略确定后，模型的执行效率仍收到数值表示、算子实现、内存访问以及运行时调度等因素的共同影响。不同的模型与应用呈现出不同的执行特征：大语言模型的上下文处理与自回归的解码在计算并行性、状态访问和时延需求上存在差异，扩散模型需要多次调用去噪声网络，而 HPC-AI 应用则涉及数值仿真、模型训练与在线推理之间的协同。因此执行优化需要在满足精度、生成质量或科学计算误差要求的前提下，从降低单次计算与访存成本、减少重复计算、改善执行组织等方面协同推进。具体而言，混合精度训练和他推理量化通过调整数值表示降低计算和存储开销；算子融合、注意力内核优化以及计算图编译提高底层的执行效率；推理调度与缓存管理改善请求处理和状态复用；面向扩散模型和 HPC-AI 工作流的优化进一步减少迭代生成成本及跨阶段等待。本节围绕以上技术展开讨论，分析其基本机制、适用条件及性能与质量之间的权衡。
6.3.1 混合精度训练与推理量化
低精度计算通过缩短权重、梯度激活的数值表示位宽，减少了显存占用和数据搬运，并调用加速器中的低精度矩阵计算单元提高计算吞吐量。在智算集群中，它的作用并不局限于单卡速度。显存占用决定了集群可承载的模型规模、批大小和并行切分方式，访存带宽决定算子能否接近计算单元的理论峰值，而数值稳定性则关系到较长周期训练能否收敛。多数加速器 FP16 和 BF16 下的矩阵乘峰值通常可以达到 FP32 路径的数倍，因此降低表示位宽往往比优化单个算子更能直接改变系统的计算吞吐量。因此，低精度是一项同时影响容量、带宽、算力和稳定性的执行优化手段。
本节覆盖训练与推理两条相对独立的技术路线。训练侧围绕 FP16、BF16 与 FP8 的精度，关注哪些张量以低精度表示，哪些状态保留较高的精度，以及缩放与回退机制如何维持收敛。推理侧则关注权重、进入矩阵乘的输入激活和 KV Cache 三类对象，形成了 W8A8、W4A16、W4A8KV4 等组合。为便于比较，本文以W8A8、W4A16 这类记法描述推理阶段的数据位宽配置，第一个数字表示线性层权重位宽，第二个数字表示矩阵乘输入激活位宽，当记法中出现 KV 时才描述 KV Cache 位宽，未出现时不做任何推断，整数与浮点数格式则另行标注。
混合精度训练在矩阵乘输入、累加结果、参数更新与持久化状态之间设计了一条精度流。Micikevivius 等在 ICLR 2018 提出的经典训练策略以 FP16 承担前向和反向的主体计算和中间存储，同时保留了 FP32 主权重，在点积与规约中使用 FP32 累加，并通过损失缩放（Loss Scaling）在反向传播前放大损失、更新前按同一个比例回缩，以避免小幅度梯度在 FP16 下溢归零。
从 FP16 到 BF16 的变化主要体现在指数与尾数的分配。BF16 保留与 FP32 相同的 8 位指数，动态范围与 FP32 近似，但尾数仅有 7 位，有效精度低于 FP16，这一取舍通常降低了训练对损失缩放的依赖，但数值检测依旧存在必要性。FP8 进一步压缩矩阵计算输入，FP8是一个格式族：E4M3的尾数更多、有效精度更好，E5M2的指数更宽，动态范围更大。一种常见的张量缩放策略在前向时使用E4M3，在反向梯度中使用E5M2，此类策略可以根据实际需求进行调整。
训练侧数据已从单层得验证推进到长程大规模训练。Scaling FP8 training to trillion-token LLMs（ICLR 2025）在 256 个 Intel Gaudi2 上训练 7B 模型，其数据规模最长约 2 万亿 token。针对短程实验未暴露的 SwiGLU 激活离群值，该工作以 Smooth-SwiGLU 抑制离群值，并将 Adam 动量一并量化为 FP8，在与 BF16 基线结果相当得同时，得到了最高约 34% 的数据提升。
显存收益则需按对象进行分解。常规的 FP8 框架主要覆盖线性层计算，优化器状态与反向所需激活仍需以 16 位保存，而激活在 Llama 系列中往往接近显存占用的一半。COAT（ICLR 2025）将二者一并量化为 FP8，并对非线性层的激活采用分组量化，在 Llama 7B、13B 和 30B 上报告相对于 BF16 的端到端显存缩减约 1.54 倍、训练加速约 1.43 倍。该比例低于位宽减半的理论值，原因是权重梯度、未量化算子与运行时工作区仍占空间，缩放因子本身也需要存储。
推理侧的低精度配置首先取决于量化对象。只压缩权重的路径通常记为 W4A16，其收益来自权重容量与读带宽下降，适合低批量、解码主导的生成阶段：GPTQ 以近似二阶信息逐列补偿量化误差，AWQ 以激活分布作为标定信号选择权重通道缩放，二者均量化激活，其系统效果依赖反量化与矩阵乘的内核融合。面向矩阵乘的联合量化以 INT8-W8A8 为代表，SmoothQuant 通过通道级等价缩放把激活函数离群值造成的量化难度迁移至权重一侧，使权重与输入激活同时进入 INT8 张量核心路径，在其测试配置下，得到了最高约 1.56 倍加速与约 2 倍内存缩减，但该结果不覆盖未量化算子、累加路径和 KV Cache。
长上下文与高并发服务还需把 KV Cache 视为独立对象，其容量随层数、KV 头数与序列长度增长，瓶颈来源与权重不同。QServe（MLSys 2025）的 QoQ 采用 INT4-W4A8KV4 配置，权重以 4 位存储、激活为 INT8、KV Cache 压至 4 位，并通过渐进式反量化把存储态的 4 位权重还原到 INT8 张量核心路径执行矩阵乘；其优势来自算法与内核的协同设计，而非全模型执行 4 位运算。综合来看，低精度能否转化为有效算力取决于模型质量、访存带宽、反量化与类型转换（cast）开销、低精度内核覆盖率（算子能否落到原生低精度路径）以及请求形态：训练侧的稳妥边界是只把矩阵乘及其输入置于低精度，保留 FP32 主权重与关键归约精度；推理侧则按瓶颈选择压缩对象。评价时应固定模型、硬件、推理后端、量化覆盖范围、批大小与输入输出长度，并同时报告困惑度、通用任务与长上下文指标；条件未对齐时，不同来源的吞吐倍率只能作为机制证据。
6.3.2 算子、内核与编译优化
6.3.1 确定了数据以何种精度存放、以何种位宽参与矩阵乘，但位宽本身不会自动转化为加速：算子如何组织、中间张量沿何种路径搬运、运行时如何生成与调度指令，仍决定这些表示能否落到加速器的原生低精度路径上。本节按新版大纲的层次展开：图级重写决定跨算子的整体计划，算子融合决定单个内核的执行边界，注意力内核体现数据移动与并行划分的具体取舍，编译与自动调优则把上述选择固化为可复用的执行计划。评价这类优化时，除端到端时延外还需记录内核数量、HBM 读写量、寄存器与共享内存占用，并区分冷启动编译时间与稳态执行时间。
神经网络中大量逐元素运算单独执行时计算量很小，却需要多次启动内核，并把中间张量反复写入和读出显存。图级重写与算子融合从两个尺度削减这部分开销：前者在计算图上做等价替换，后者把生产者与消费者放进同一内核。TASO（SOSP 2019）不再依赖人工设计的变换规则，而是以给定算子为基本构件自动生成候选替换，并用定理证明器验证语义等价，在新增算子持续出现时保持可扩展性。Apollo（MLSys 2022）在同一框架内同时处理访存受限与计算受限的算子，把图级节点分组与算子级循环融合结合以扩大搜索空间，并让下游循环优化器的反馈反向上传，促使图引擎重新生成适合下游的分区模式，从而缓解融合方案无法落地的可扩展性问题；在训练负载上，它相对 TensorFlow 与 XLA 在单 GPU 上分别提升 1.86 倍与 1.37 倍，多 GPU 上提升 1.96 倍与 1.18 倍，在领域专用加速器上把厂商框架性能提升 19.7%。Welder（OSDI 2023）从访存一侧切入，其 tile-graph 抽象在 tile 粒度管理数据，利用内存层级之间优化相互独立的特点把组合优化空间拆分为若干独立子空间，并以 tile 流量成本模型在算子内与算子间数据复用之间权衡；该工作观测到现代 DNN 的显存带宽利用率可高达 96.7%，而计算核心平均利用率仅 51.6%，据此生成的执行计划包含 89 种以上优化模式并优于同期方案。
融合并非越深越好，其边界由资源与下游接受度共同决定。融合后的内核通常占用更多寄存器与共享内存，可能降低并发驻留的线程块数量；若融合结果无法被下游调度或代码生成阶段有效接受，收益还会被抵消，这也是 Apollo 需要向下游反馈分区模式的原因。此外，访存受限算子适合通过融合减少中间张量往返，而本身接近计算峰的矩阵乘收益有限，AStitch（ASPLOS 2022）正是面向内存密集算子扩展多维优化空间的代表工作。因此融合的范围与粒度更适合由编译器在给定形状、后端与资源约束下搜索决定，而非按固定规则展开。
注意力是执行组织影响最明显的算子。长度为 N 的序列通常涉及 N×N 的注意力分数与概率矩阵，若将其完整写入显存，中间数据的搬运量会抵消计算收益，而近似注意力方法在降低计算复杂度的同时常无墙钟收益。FlashAttention（NeurIPS 2022）把注意力算法显式设计为访存感知：将 Q、K、V 分块载入片上存储逐块计算，以在线 softmax 维护每行截至当前的最大值、指数和与加权输出，使完整分数矩阵无需物化，反向传播则通过重算中间量减少保存开销；其 IO 复杂度分析表明 HBM 访问次数低于标准注意力，并对一定规模的片上存储达到最优。实验中，BERT-large（序列长度 512）相对 MLPerf 1.1 训练记录取得 15% 的端到端墙钟加速，GPT-2（序列长度 1K）加速 3 倍，长程竞技场任务（序列长度 1K—4K）加速 2.4 倍。需要强调的是，它仍是精确注意力，改进的是数据移动与执行组织，稠密注意力的二次计算规模并未改变。
此后的工作主要解决内核的资源利用与工程适配问题。分块与在线 softmax 使注意力显存占用由二次降为线性，并相对优化基线取得 2—4 倍运行时加速，但在 A100 上仅达到理论最大吞吐的 25%—40%，原因是线程块与 warp 之间的工作划分不佳。FlashAttention-2（ICLR 2024）因此减少非矩阵乘浮点运算、允许单个注意力头跨线程块并行以提高占用率，并在 warp 之间重新分配工作以减少共享内存通信，结果相对前代约快 2 倍，在 A100 上达到理论峰值吞吐的 50%—73%，端到端训练 GPT 类模型时每张 A100 达到 225 TFLOPs/s，相当于 72% 的模型浮点运算利用率。FlashAttention-3（NeurIPS 2024）转向 Hopper 平台的异步能力：前一版本在该类 GPU 上仅有 35% 利用率，新版本利用张量核心与 TMA 的异步特性，通过 warp 专用化重叠计算与数据搬运、交错块级矩阵乘与 softmax，并借助块量化与低精度路径压缩数据量，在 H100 上取得 1.5—2.0 倍加速，FP16 达到 740 TFLOPs/s（75% 利用率），FP8 接近 1.2 PFLOPs/s，其 FP8 路径的数值误差较基线 FP8 注意力低 2.6 倍；低精度在此只作为内核可用的执行条件，其格式与缩放方案已在 6.3.1 讨论。面向服务场景，FlashInfer（MLSys 2025）把可组合性与工程约束作为重点：以块稀疏与可组合格式应对 KV Cache 的存储异构、降低访存冗余，提供可通过即时编译适配不同配置的注意力模板，并以负载均衡调度适应用户请求的动态性，同时保持与需要静态配置的 CUDA Graph 兼容；它已被 SGLang、vLLM 与 MLC-Engine 等框架采用，在服务基准上相对编译器后端降低 29%—69% 的 token 间时延，长上下文推理延迟降低 28%—30%。
训练与预填充阶段的注意力以大块矩阵运算为主，单步解码则相反：查询数量很少，却要访问不断增长的历史 KV 状态，并行与归约的划分方式不同。FlashDecoding++（MLSys 2024）把该阶段的低效归为三类：部分 softmax 结果需要同步更新，在注意力计算中带来约 20% 开销；推理中的矩阵乘形状偏扁平，补齐零值的做法可造成超过 50% 的性能损失；数据流静态固定时，不同形状矩阵乘之间的性能波动可达 50.25%。该工作以统一最大值的异步 softmax 消除同步，用双缓冲改善扁平矩阵乘，并按输入特征与硬件资源启发式选择数据流，在其测试中相对 Hugging Face 实现于 NVIDIA GPU 上取得最高 4.86 倍、AMD GPU 上 2.18 倍加速，相对当时主流推理引擎平均加速 1.37 倍。这些倍率绑定其模型与后端配置，不能直接推广到训练侧注意力。
单算子与内核层面的优化需要在更大范围上固化，这正是图编译与自动调优的职责。编译过程覆盖图捕获、等价变换、算子融合、布局选择、内存规划与低层代码生成，其难点在于把图级决策稳定映射到具体硬件。TVM（OSDI 2018）以图级与算子级优化的组合实现跨后端性能可移植，用学习型成本模型自动化低层程序搜索，并在低功耗 CPU、移动 GPU 与服务器 GPU 上取得与手工调优库相当的性能，同时支持 FPGA 等新后端。Ansor（OSDI 2020）从搜索空间的分层表示中采样程序，再以进化搜索与学习型成本模型筛选，并用任务调度器同时优化多个子图，在 Intel CPU、ARM CPU 与 NVIDIA GPU 上相对当时最优分别取得最高 3.8 倍、2.6 倍与 1.7 倍提升；ROLLER（OSDI 2022）走另一条路线，用构造式编译直接生成张量程序而非大规模搜索，其价值在于把编译时间本身压缩到可用范围。TensorIR（ASPLOS 2023）把张量计算提升为循环嵌套表示中的一等对象，使编译器能直接调用硬件张量原语，跨平台性能与手工优化系统相当；PyTorch 2（ASPLOS 2024）则给出生产级路径，其中 TorchDynamo 是 Python 层的即时编译器，通过动态修改字节码在不牺牲 Python 灵活性的前提下获得可编译的计算图，TorchInductor 负责生成内核，Triton 一类 tile 级 DSL 则为这类代码生成提供了更贴近硬件的表达方式。
综合来看，执行优化的收益来自数据移动、内核组织与编译计划的配合，且不能简单相乘：低比特权重减少了读取量，若反量化与类型转换成为新瓶颈，应回到反量化与矩阵乘的融合上；继续降低位宽或无限扩大融合范围，未必带来端到端改善。评价时应固定模型、形状分布与硬件后端，同时报告内核数量、访存流量、占用率与稳态时延，并单独说明编译与搜索本身的时间成本。

6.3.3 大模型推理执行优化
6.3.2 的内核与编译优化改善单次前向的执行效率，而服务系统的有效吞吐还取决于另一组因素：请求如何在时间上被组织、状态如何在显存中被管理、重复计算能否被复用。大模型推理包含特征不同的两个阶段：预填充（prefill）处理完整输入提示并产生首个输出 token，计算密集、单次延迟较高；解码（decode）逐 token 生成后续内容，访存密集而算力利用率偏低。本节沿一次请求的生命周期，依次讨论批处理与调度、KV Cache 内存管理、前缀复用、两阶段分离部署与投机解码；评价时需把吞吐与首 token 时延（Time to First Token，TTFT）、每输出 token 时延（Time Per Output Token，TPOT）放在同一口径下给出。
早期的批处理以请求为粒度：一批请求同时进入执行，直到全部完成后才释放批次，长度差异使短请求被迫等待长请求，显存也需按批内最长序列预留。Orca（OSDI 2022）把调度粒度改为单次迭代，由调度器在每个解码步重新组批，并只对适合批处理的算子应用批处理，从而在迭代之间动态加入新请求、移除已完成请求；在 GPT-3 175B 上，它相对 NVIDIA FasterTransformer 在相同延迟水平下取得 36.9 倍吞吐提升。Sarathi-Serve（OSDI 2024）进一步处理预填充对解码的阻塞：把预填充拆分为近似等长的块并插入正在进行的解码批次，形成无停顿调度，同时以较均匀的批次减少流水线气泡；在尾延迟约束下，Mistral-7B 单张 A100 的服务容量相对 vLLM 提升 2.6 倍，Yi-34B 双卡提升 3.7 倍，Falcon-180B 结合流水并行时端到端容量提升最高 5.6 倍。这些倍率描述的是满足延迟约束时每张 GPU 可承载的请求量，不等同于无约束峰值吞吐。
KV Cache 是服务并发的主要制约。其容量随层数、KV 头数、序列长度与并发数增长，并随请求生成与结束动态伸缩；若按最大长度连续预留，碎片与重复副本会显著浪费显存并压低批大小。PagedAttention（SOSP 2023）把操作系统中的分页思想引入注意力计算：将 KV 按固定大小的块管理，逻辑块经映射表指向物理块并按需分配，同时支持请求内部与请求之间的块共享；在此基础上实现的 vLLM 使 KV Cache 接近零浪费，在相同延迟水平下相对 FasterTransformer、Orca 等系统把吞吐提升 2—4 倍，且序列更长、模型更大、解码算法更复杂时提升更明显。当服务规模继续扩大，KV 的存放位置也不再局限于单机显存。Mooncake（FAST 2025）以 KVCache 为中心构建分离式架构，既把预填充与解码集群分开，也把 GPU 集群中未被充分利用的 CPU、DRAM、SSD 与网卡资源组织为分离式 KV Cache，通过全局缓存与调度器在遵守严格延迟 SLO 的前提下提高吞吐；在真实请求轨迹下，其有效请求容量相对基线提升 59%—498%，实际部署中使同一服务在 A800 与 H800 集群上分别多承载 115% 与 107% 的请求。需要区分的是，解码内核本身的并行划分已在 6.3.2 讨论，此处关注的是状态的管理与存放方式。
多轮对话、检索增强生成与智能体程序会反复提交相同或高度重叠的提示前缀，重复的预填充因此成为可消除的开销。SGLang（NeurIPS 2024）由前端语言与运行时两层构成，运行时以基数树组织 KV Cache，使共享前缀只计算一次并自动匹配可复用部分，同时用压缩有限状态机加速结构化输出的解码；其评估覆盖智能体控制、逻辑推理、少样本学习、JSON 解码、检索增强生成与多轮对话等任务，吞吐相对当时最优系统最高提升 6.4 倍。Prompt Cache（MLSys 2024）把可复用的文本段显式定义为 prompt module，预先计算并存储其注意力状态，并以模式约束保证复用时的位置正确，其测得的 TTFT 改善从 GPU 推理的 8 倍到 CPU 推理的 60 倍，且不修改模型参数。当共享前缀超出内存容量而必须下沉到磁盘时，复用未必仍然划算：IMPRESS（FAST 2025）指出磁盘 I/O 延迟会抵消收益，因此只把重要的前缀 KV 装入上层存储，其依据是不同注意力头的重要 token 索引集合高度相似，并据此设计了 I/O 友好的重要 KV 识别算法与多级存储策略。前缀复用节省的是预填充阶段的重复计算，解码阶段逐 token 的固定成本不受影响。
预填充与解码对资源的需求不同，共置在同一组 GPU 上会产生相互干扰，并把两者的资源分配与并行策略耦合在一起。DistServe（OSDI 2024）把两个阶段分派到不同 GPU 以消除干扰，并按应用的 TTFT 与 TPOT 要求分别协同优化资源分配与并行策略，同时依据集群带宽决定两阶段放置以降低拆分通信；在其评估中，满足延迟约束时每张 GPU 可服务的请求数相对当时系统提升至 7.4 倍，或在同等服务能力下把 SLO 收紧 12.6 倍，且超过 90% 的请求满足约束。Splitwise（ISCA 2024）从硬件成本出发得到相近结论：token 生成阶段算力利用不足，可使用功耗与成本更低的设备，两阶段借助高速背板互联完成状态转移，从而在成本降低约 20% 的同时获得 1.4 倍吞吐，或在同等成本与功耗下把吞吐提升至 2.35 倍。Mooncake 则说明分离式架构在集群级还可与 KV 存储分层结合，把两阶段分离与缓存调度统一考虑。
投机解码针对自回归解码的串行性。解码每一步都要把全部模型参数从高带宽显存搬入计算单元，而单步只产生一个 token，减少串行步数因此最直接。投机解码（ICML 2023）用较小的草稿模型生成若干候选 token，再由目标模型并行验证，并按校正后的采样规则接受或拒绝，在不改变输出分布的前提下缩短解码路径，且无需重新训练或改动模型结构；在 T5-XXL 上相对 T5X 实现取得 2—3 倍加速，输出完全一致。后续工作分两条路线：SpecInfer（ASPLOS 2024）把候选组织为 token 树，用树状并行解码一次性验证多条路径，在分布式推理中相对现有服务系统提升 1.5—2.8 倍、在参数卸载场景提升 2.6—3.5 倍；EAGLE（ICML 2024）与 Medusa（ICML 2024）改变草稿来源，前者在特征层进行自回归预测并借助超前一步的 token 序列消除特征级不确定性，在 LLaMA2-Chat 70B 上取得 2.7—3.5 倍延迟加速与约两倍吞吐，后者在主干模型上增加额外解码头、以树状注意力同时验证多条候选，冻结主干时加速超过 2.2 倍、与主干联合微调后达到 2.3—3.6 倍。这类方法的收益取决于候选接受率与验证开销，接受率偏低时额外前向计算可能抵消缩短的步数。
上述手段作用于推理服务的不同环节：调度决定请求如何共享算力，显存管理决定可并发的请求规模与状态存放层级，前缀复用消除重复的预填充，两阶段分离让资源与并行策略各自匹配，投机解码压缩串行步数。它们之间存在耦合，例如更大的批会加剧显存压力，更长的提示会放大预填充与解码之间的干扰，因此各项收益不能简单相加或相乘。评估时应固定模型与版本、硬件、推理后端、输入输出长度与并发水平，并同时给出 TTFT、TPOT 以及延迟约束下的服务容量；只报告无约束吞吐，会把延迟代价隐藏在平均值之下。
6.3.4 Diffusion模型执行优化
扩散模型与自回归语言模型的执行特征不同：它的生成过程是一段固定的多步去噪序列，每一步都调用同一个去噪网络，总开销近似等于迭代步数与单步成本的乘积。因此其执行优化集中在三个方向：减少迭代步数、降低单步计算量，以及在多个设备上分摊同一步的计算。评价因此有专门口径：函数评估次数（Number of Function Evaluations，NFE）反映迭代规模，FID、CLIP 与 VBench 等指标反映生成质量，二者必须同时给出。本节按新版大纲的顺序，依次讨论少步采样与快速求解器、蒸馏与一致性模型、跨时间步特征缓存，以及面向高分辨率生成的多 GPU 并行与通信隐藏。
原始采样需要数百至数千次串行函数评估。DDIM（ICLR 2021）通过构建一类非马尔可夫扩散过程改变这一状况：它与 DDPM 具有相同的训练目标，但反向过程可用更少的步骤完成，墙钟时间相对 DDPM 快 10—50 倍，并允许在计算量与样本质量之间连续权衡。更系统的思路是把采样视为求解扩散常微分方程：DPM-Solver（NeurIPS 2022）给出扩散 ODE 解的精确形式，把解的线性部分解析求解，经变量替换化为神经网络输出的指数加权积分，并据此构造具有收敛阶保证的专用高阶求解器；它无需额外训练，同时适用于离散与连续时间模型，在 10—20 次函数评估内即可生成高质量样本，CIFAR-10 上 10 次评估的 FID 为 4.70、20 次为 2.87，相对此前免训练采样器取得 4—16 倍加速。UniPC（NeurIPS 2023）针对极少步（少于 10 步）场景改进：它提出的统一校正器可接在任意已有采样器之后提升精度阶数而不增加模型评估次数，统一预测器则支持任意阶数，二者组合成统一的预测—校正框架，在 10 次函数评估下于 CIFAR-10 无条件生成取得 3.87 的 FID、于 ImageNet 256×256 有条件生成取得 7.51 的 FID。DPM-Solver++（Machine Intelligence Research 2025）补充了关键限制：高阶方法在无引导采样下表现良好，但在引导采样中会出现不稳定，引导尺度增大时甚至慢于作为一阶求解器的 DDIM；它改用数据预测模型求解 ODE 并引入阈值方法使解与训练数据分布保持一致，再以多步变体降低有效步长，使像素空间与潜空间的引导采样在 15—20 步内达到高质量。可见步数压缩不是普适结论，其成立取决于引导方式与求解器稳定性。
另一条路线直接改变模型本身。渐进蒸馏（ICLR 2022）把训练好的确定性采样器蒸馏为步数减半的新模型，并对结果反复施加同一过程，使步数逐轮减半；在 CIFAR-10、ImageNet 与 LSUN 上，其起点为最高 8192 步的采样器，最终降到 4 步而感知质量损失不大，CIFAR-10 上 4 步的 FID 为 3.0，且完整的渐进蒸馏训练时间不超过训练原模型所需时间。一致性模型（ICML 2023）直接学习从噪声到数据的映射，支持一步生成，也允许多步采样在计算与质量之间权衡；它既能由预训练扩散模型蒸馏得到，也可作为独立生成模型训练，一步采样在 CIFAR-10 上取得 3.55 的 FID、在 ImageNet 64×64 上取得 6.20，并支持修复、上色与超分等零样本编辑。当这类方法扩展到文生图与视频等大规模任务时，瓶颈转到潜空间：Improved Training Technique for Latent Consistency Models（ICLR 2025）发现潜空间数据含有高度脉冲式的离群值，会显著削弱原有训练技术，于是以 Cauchy 损失替代 Pseudo-Huber 损失、在早期时间步引入扩散损失、采用最优传输耦合，并配合自适应调度与非缩放 LayerNorm，训练出可在一步或两步内采样的潜一致性模型。这类方法的共同代价是一次性训练投入，且步数压缩存在质量下限。
在不对模型做任何改动的前提下，缓存利用相邻去噪步之间的时间冗余。DeepCache（CVPR 2024）依据 U-Net 的结构特点，复用相邻步骤的高层特征而以较低成本更新低层特征：在 Stable Diffusion v1.5 上取得 2.3 倍加速，CLIP 分数仅下降 0.05；在 LDM-4-G 上取得 4.1 倍加速，ImageNet 上 FID 仅上升 0.22，并能与既有采样器叠加。面向扩散 Transformer，Learning-to-Cache（NeurIPS 2024）把缓存的基本单位下沉到单个网络层，以可微优化目标训练一个与输入无关、随扩散时间步变化的路由器，从而在指数级的层组合空间中确定哪些层可以缓存复用并最终给出静态计算图；在 U-ViT-H/2 上，缓存步可移除高达 93.68% 的计算（全部步骤计为 46.84%），而 FID 下降不足 0.01。面向视频生成的 TeaCache（CVPR 2025）修正了缓存的时间粒度：此前方法在时间步上均匀选取缓存点，但模型输出之间的差异在各时间步并不均匀；它以计算代价很小、且与输出强相关的模型输入作为差异代理，先经时间步嵌入调制再重缩放修正，用其判断是否复用缓存，相对 Open-Sora-Plan 取得最高 4.41 倍加速，VBench 分数仅下降 0.07%。缓存以近似换取计算量下降，其收益取决于时间冗余的强度与缓存的粒度选择。
高分辨率生成还会触及单卡的显存与延迟上限，需要把同一步计算分摊到多张 GPU。DistriFusion（CVPR 2024）把输入切分为多个 patch 并分配到不同 GPU，但直接划分会切断 patch 之间的交互、损失保真度，补上交互又会带来巨大通信开销；它利用相邻去噪步输入高度相似这一点，复用上一时间步已计算的特征图为当前步提供上下文，这种位移 patch 并行使跨卡通信能够异步进行并与计算形成流水，应用于 Stable Diffusion XL 时在 8 张 A100 上相对单卡取得最高 6.1 倍加速且无明显质量退化。PipeFusion（NeurIPS 2025）进一步把并行维度扩展到模型层，把图像切分为 patch 的同时把模型层分布到多张 GPU，采用 patch 级流水并行编排通信与计算，并同样复用一步陈旧的特征图提供上下文；相比张量并行、序列并行与 DistriFusion，其通信开销显著降低，同时通过参数分布提升显存效率，因而适用于 Flux.1 一类更大的 DiT，在 8×L40 PCIe 上对 Pixart、Stable Diffusion 3 与 Flux.1 取得当前最优性能。多卡方案的收益同时依赖时间冗余与互联带宽，patch 之间的交互越强、可隐藏的通信越有限。
上述路线分别作用于迭代步数、单步成本与并行度，三者可以叠加，但收益不能简单相乘：少步采样与特征缓存压缩的是同一类时间冗余，同时启用时的加速比会低于两者单独加速比的乘积；蒸馏改变了模型参数，需要在新模型上重新评估质量；多卡并行的收益则受 patch 交互强度与互联带宽约束。评价扩散模型执行优化时，应固定模型与检查点、分辨率、采样步数、引导尺度与随机种子，同时报告函数评估次数、端到端时延以及 FID、CLIP 或 VBench 等质量指标；只给出加速倍率而缺少质量口径，会使不同工作之间的比较失去意义。
6.3.5 HPC-AI代理计算与混合工作流
前面三节讨论的负载以深度学习模型本身为主体，HPC-AI 场景的执行特征则不同：数值仿真与 AI 计算在同一套系统上交替或并发运行，数据在仿真器与模型之间持续流动，优化的对象也从单次前向扩展到跨阶段的作业编排。低精度、内核与推理侧的优化在闭环内部同样适用，但本节关注的是工作流层面的执行组织，即如何用学习模型替代部分数值求解、如何让仿真与推理在同一作业内协同，以及用什么指标判断这类协同是否真的有效。下文的讨论依次覆盖代理模型的能力与边界、仿真—训练—推理闭环的耦合方式，以及面向超算的评价方法。
传统数值求解面对的是一族方程而非单个实例：同一套偏微分方程需要在大量参数取值下反复求解，每次都要重新迭代。神经算子把学习对象从有限维空间之间的映射推广到函数空间之间的映射，因而一次训练即可覆盖参数的连续变化。DeepONet（Nature Machine Intelligence 2021）用两个子网络实现这一映射：branch net 编码输入函数在固定数量传感器处的取值，trunk net 编码输出函数的位置坐标，其设计动机是把算子通用逼近定理转化为可训练的模型，并在动态系统与偏微分方程上显著降低泛化误差，同时从理论上给出近似误差与传感器数量的关系。Fourier Neural Operator（ICLR 2021）则把积分核直接在频域参数化，在 Burgers 方程、Darcy 流与 Navier-Stokes 方程上验证；它是首个能成功建模湍流并具备零样本超分辨能力的机器学习方法，相对传统偏微分方程求解器快最多三个数量级，在固定分辨率下精度也优于此前基于学习的求解器。Neural Operator（JMLR 2023）为这类方法提供了统一形式，即线性积分算子与非线性激活函数的复合，证明了相应的通用逼近定理，并指出其离散不变性——不同离散化之间共享同一组模型参数；该工作还归纳了图神经算子、多极图神经算子、低秩神经算子与 Fourier 神经算子四类高效参数化。代理模型的替代对象是重复求解过程，其精度仍受训练数据分布约束。
代理模型在真实业务系统中的规模可由天气预报说明。GraphCast（Science 2023）直接从再分析数据训练，可预测数百个天气变量、覆盖全球 0.25° 分辨率、给出 10 天预报，单次预报耗时不到一分钟；在 1380 个验证目标中，它在 90% 的目标上显著优于当时最准确的业务确定性系统，并支持对热带气旋、大气河与极端温度等事件的更好预测。这一结果的意义在于把原本需要数小时超算资源的中期预报压缩到分钟级，同时也界定了适用条件：预报质量来自训练数据覆盖的气象分布，面对分布外情形与极端事件仍需额外验证，因此代理模型适合作为高成本数值流程的替代入口，而不是在所有情形下取消数值求解。
闭环的另一端是把推理放回仿真过程内部。SmartSim（Journal of Computational Science 2022）面向传统 HPC 仿真提供在线分析与机器学习能力，使仿真与推理在异构系统上共享同一模型：其演示运行了一个 12 成员的全球尺度高分辨率海洋模拟集成，每个成员跨越 19 个计算节点，并在每个模拟时间步调用同一套模型架构，累计服务约 9700 亿次推理，这是首次在气候尺度海洋模拟中通过分布式在线深度神经网络推理获得改进。Coupling Streaming AI and HPC Ensembles（IPDPS 2022）提出 ML 驱动的 steering 框架 DeepDriveMD：让模型在线筛选更具科学意义的计算路径，从而把算力集中到更可能产生结果的轨迹上，在蛋白质折叠问题上取得 100—1000 倍加速。这类闭环的关键工程问题不在模型本身，而在于仿真与推理的任务异构性、两者的资源并置或分离方式，以及数据能否在内存中直接交换而非经由文件系统往返。
当闭环由多个阶段和多种任务类型构成时，编排方式决定了资源能否被持续利用。Colmena（IJHPCA 2025）指出，工作流是超算上常见的一类应用，但其松散耦合与异构特性常使其无法充分利用机器能力；Colmena 允许科学家以协作智能体的形式定义应用如何响应事件（例如任务完成），由运行时在执行过程中学习并调整工作流。该工作在超算规模部署中总结了三个具体挑战：设计能够最大化节点利用率的 steering 策略、引入降低数据密集任务通信开销的数据织物，以及在多次调用之间缓存代价高昂的操作；这些机制已在化学、生物物理与材料领域支撑了相应的科学进展。更早的工作中，DeepDriveMD（DLS@SC 2019）从蛋白质折叠的高维构象空间与采样不足问题出发验证了机器学习引导仿真的可行性，Colmena（MLHPC@SC 2021）则给出了这一路线的早期系统形态。闭环的收益并非自动成立：若推理在等待仿真产出数据、或仿真在等待推理结果，节点仍会空转，因此调度与数据通路的设计直接决定加速能否兑现。
评价这类系统需要同时覆盖系统指标与科学指标。系统侧应报告节点与 GPU 利用率、任务排队与空闲时间、数据搬移量与内存交换比例、缓存命中情况、扩展效率以及 time-to-solution；科学侧则应说明在相同算力预算下获得的有效样本、收敛速度或发现数量。公开基准目前只覆盖其中一部分：MLPerf HPC（MLHPC@SC 2021）以训练任务为主，可用于比较机器学习负载在超算上的实现效率，但不能单独代表动态的 AI–HPC 闭环；AI-Enabling Workloads on Large-Scale GPU-Accelerated Systems（HPCA 2022）提供了生产级 GPU 加速系统上 AI 工作负载资源行为的实测依据，可用于校准对利用率与数据通路的预期。因此，AI–HPC 闭环的评价更适合采用"系统开销 + 科学产出"的组合口径，而非单一的加速倍数。
综合来看，代理模型降低的是单次求解成本，在线闭环改变的是计算顺序，编排与调度决定的则是资源能否被持续利用，三者的收益不能简单相乘：代理模型的精度不足会把节省下来的算力重新浪费在无效仿真上，闭环中的同步等待会抵消推理带来的时间收益，调度不当则会使机器学习任务与仿真任务相互争抢资源。HPC-AI 工作流的优化目标因此不是单次前向的峰值效率，而是单位算力所换得的科学产出；评价时应固定应用、输入规模、模型精度门槛与系统配置，并同时给出系统指标与科学指标，才能判断协同是否真正有效。
6.4 大规模集群可靠性与容错
6.4.1 集群故障特征与可观测性
规模扩大带来的第一个后果是故障从偶发事件变成常态：单组件的低故障率在数万卡规模与数周训练时间下会转化为频繁的作业中断与性能退化。大语言模型的训练基础设施因此需要同时满足三个目标——最小化训练中断、高效完成故障诊断、提供有效的容错能力（ByteRobust，SOSP 2025）。本节与后续小节按“故障观测与诊断—训练状态保存—故障恢复与弹性训练—在线推理高可用”的链路展开，先讨论故障如何被看见。
表征研究给出了故障的基本图景。Characterization of Large Language Model Development in the Datacenter（NSDI 2024）基于某 GPU 数据中心六个月的 LLM 开发负载轨迹，指出 LLM 与传统任务专用深度学习在工作模式与资源需求上的差异，使此前针对后者的分析结论不再适用，而频繁的硬件故障、复杂的并行策略与不均衡的资源利用是实际开发中的主要挑战。MegaScale（NSDI 2024）则给出万卡以上规模的工程经验：在超过 10,000 张 GPU 上训练大模型对效率与稳定性提出空前要求，其做法是在模型块与优化器设计、计算与通信重叠、算子优化、数据管线与网络性能调优等层面进行全栈协同设计，说明稳定性并非单一组件问题。Google TPUv4 的运营实践提供了另一类平台的对照：故障处理与作业管理需要在硬件、调度与软件之间形成闭环，不同加速器的故障分布与恢复方式也因此不同。
可观测性需要分层建立，而不能依赖单一指标。面向设备的监控给出 GPU、CPU、网卡等部件的性能计数器，其采样粒度通常只有秒级，且为避免影响生产，仅能选择少量关键函数进行监测；当问题出现在缺少观测的层次时，作业可能表现为静默超时、性能缓慢劣化或不可解释的挂起（EROICA，NSDI 2026）。因此近年的基础设施实践把指标体系扩展到设备、节点、网络、集合通信、作业与模型数值行为多个层次，并要求监测、关联分析、诊断与恢复形成闭环（ByteRobust，SOSP 2025）；针对训练发散的异常诊断（FLARE，NSDI 2026）进一步把关注点从“作业是否失败”扩展到“作业是否在收敛”。这一层次的难点在于跨层关联：同一次性能退化可能同时表现为通信等待、显存压力与算子效率下降，只有把应用语义与硬件指标对齐，才能确定真正的触发点。
按使用方式区分，排障手段可分为三类。健康基准在作业之外预先验证硬件，以主动方式暴露潜在问题；在线剖析在不中断生产的前提下采集细粒度信息，EROICA（NSDI 2026）即定位为首个同时提供细粒度观测与全训练覆盖的在线排障系统，用以弥补“另建小规模测试环境”这一传统做法的时效性与可行性不足；按异常触发的细粒度追踪则只在检测到异常后提高采样密度，以控制开销。三者对应不同的时间粒度与覆盖范围，其取舍是排障体系设计的核心：覆盖率越高、粒度越细，运行开销越大，而开销本身又会改变被观测对象的性能。
工具层面已有成熟的工程接口。DCGM 及其诊断模块提供设备级健康与计数信息，Nsight Systems 提供时间线级别的剖析，PyTorch Profiler 提供框架层的算子与内存视图；这些官方工具适合作为采集与展示手段，但其输出本身不构成可靠性结论，故障归因仍需结合作业语义与对照实验。综合来看，可观测性建设的评价维度应包含覆盖范围、运行开销、时间粒度与根因定位能力；仅报告“采集了哪些指标”，无法说明诊断体系是否有效。
6.4.2 故障诊断、落后者定位与主动隔离
集群故障可按表现分为三类：fail-stop 使进程或节点直接退出，检测相对容易；fail-slow 不引发崩溃，却持续拖慢训练进度；静默数据损坏（Silent Data Corruption，SDC）既不报错也不明显变慢，但会破坏结果正确性。后两类是超大规模训练的治理难点，因为同步式的训练流程会把单个组件的异常放大为整批作业的等待。
GREYHOUND（USENIX ATC 2025）对共享生产集群中超过 10,000 张 GPU 的长期观测说明，fail-slow 通常表现为瞬态掉队：其成因包括资源争用、设备退化与网络拥塞引起的慢计算或慢通信，持续时间从不足一分钟到接近十小时，平均使大型训练作业的进度延迟 1.34 倍。该结果说明掉队既非稳定复现，也不局限于单一部件，因此检测手段需要结合指标模式、训练不变量与真实负载回放，并在误报与漏报之间权衡：漏报会让异常长期存在，误报则会触发不必要的作业中断与节点隔离。除性能异常外，SDC 类灰故障代表着另一类风险，其特点是硬件在常见压测下表现正常，仅在生产负载的数据相关路径上出错，因此单纯依赖吞吐与延迟监测无法覆盖（SDCs in the Wild，OSDI 2026）。
通信侧的诊断需要打开集合通信库这一黑盒。Mycroft（SOSP 2025）指出，集合通信库管理着训练框架定义的数据传输，其控制流与数据流复杂，却在故障定位时缺少必要信息，因此以轻量分布式追踪记录集合通信状态并据此做根因分析。慢链路的影响往往并不止于链路本身：拥塞、网卡或交换机缺陷以及拓扑不对称会改变集合通信的完成时间，进而在流水线并行中转化为气泡，使与故障设备并无直接依赖的阶段一并等待。把诊断结果衔接为缓解动作，是这一环节与纯监控的区别所在。
落后者定位的核心判断是“慢组件不一定决定端到端性能”。Understanding Stragglers in Large Model Training Using What-if Analysis（OSDI 2025）基于字节跳动五个月的轨迹指出，掉队并非总是硬件故障所致，而可能来自多种复杂因素，同时传统依赖备份 worker 的缓解方案隐含“掉队不频繁”的前提，在大规模混合并行训练中并不成立。该工作因此采用反事实分析，评估移除或替换某个慢组件后端到端性能会如何变化，从而区分关键路径上的落后者与虽有异常但不影响全局的组件；Holmes（NSDI 2025）从异常迭代的定位角度补充这一能力，EROICA（NSDI 2026）则提供在线剖析证据。只有落到关键路径上，隔离与绕行动作才有意义。
主动隔离与健康管理构成诊断之后的闭环。SuperBench（USENIX ATC 2024）主张用主动验证替代被动等待：在作业准入前对节点执行健康基准，运行期维持健康评分，出现异常后隔离并维修，再经重新验证回到资源池。该工作同时提示通用压力测试对数据相关 SDC 的漏检风险，因此修复后的验证需要尽量贴近真实负载。生产平台的实践也表明，健康管理需要与调度、维修流程和资源池准入规则联动，否则隔离会长期占用容量而无从恢复（TPUv4 Resiliency，NSDI 2024；ByteRobust，SOSP 2025）。
综合来看，这一环节的收益取决于诊断精度与处置成本的平衡：检测过于敏感会把可用节点踢出资源池，过于迟钝则让落后者在关键路径上持续放大。评价相应工作时应同时报告检测的误报率与漏报率、根因定位所需时间、隔离与恢复动作的资源代价，以及这些机制在真实作业而非合成故障上的效果。
6.4.3 分布式检查点与训练状态保存
故障恢复的前提是训练状态被正确保存。需要持久化的不只是模型参数，还包括优化器状态、随机数状态与数据加载游标，否则续跑后的训练轨迹无法与原作业一致；在混合并行下，这些状态按张量并行、流水线并行与数据并行的布局分散在不同设备上，直接把各设备的本地状态落盘会产生与并行配置绑定的检查点。
因此分布式检查点的核心能力是重分片。ByteCheckpoint（NSDI 2025）面向大模型开发的全流程指出，检查点不仅用于故障续训，还用于 GPU 资源与并行配置变化后的恢复、跨训练阶段的状态迁移以及向评估任务的派发，这些场景都要求把检查点从一种并行布局转换到另一种。Universal Checkpointing（USENIX ATC 2025）进一步以通用格式支持跨并行配置的重载，PyTorch 的分布式检查点接口则提供了同类能力的工程实例。重分片的代价在于元数据管理与读写路径的复杂度，若并行度变化频繁，转换本身会成为新的开销来源。
异步检查点把保存动作从训练关键路径上移开。PCcheck（ASPLOS 2025）提出并发检查点机制，允许高频保存且开销很小，并支持持久化到 SSD 与持久内存，从而在“保存频率越高恢复代价越低、但高频保存本身开销越大”的矛盾中给出折中。DataStates-LLM（HPDC 2024）采用延迟异步的多级检查点，把状态先落在近端存储再逐步下沉；Checkmate（NSDI 2026）则从网络侧入手，借助梯度复制实现近乎零开销的保存，但其前提是特定的数据并行结构与额外资源。CheckFreq（FAST 2021）是这一路线的早期代表，它指出传统按 epoch 保存的方式在现代模型上意味着数小时的重算，因而转向细粒度、高频次的保存。异步化的代价是写时一致性：训练状态在后台写入期间仍在变化，需要通过版本控制或影子副本保证检查点内部一致。
增量与分层检查点减少的是数据量。LowDiff（SC 2025）把差分检查点从推荐系统推广到通用分布式训练：既然相邻迭代之间参数变化有限，就不必反复写入全量状态。Gemini（SOSP 2023）则从存储层级入手，把检查点写入主机 CPU 内存，从而摆脱远程存储带宽的限制，在大型模型训练中实现逐迭代的检查点频率且不对训练吞吐产生额外开销。对稀疏结构，只保存变化部分收益更加明显，例如 MoE 训练中只持久化被激活的专家片段。分层保存的代价是恢复链变长：状态分布在 GPU、CPU 内存与持久存储之间，任何一层缺失都需要重新计算或重新加载。
检查点频率的选择本质上是一个期望损失问题。CheckFreq（FAST 2021）给出的权衡框架包含四项输入：故障到达率、单次保存的开销、可接受的重复计算量以及存储带宽；频率提高会缩短平均回滚距离，但保存开销会直接侵蚀训练吞吐。异步与增量技术的作用正是把“单次保存开销”这一项压到更低，从而把可行频率提高到逐迭代量级（AdaCheck，FAST 2026；PCcheck，ASPLOS 2025）。评价这类系统时应同时报告保存开销、检查点总量、恢复时间与被截断的重算量，并明确其依赖的存储层级与并行度假设，否则不同方案的收益无法比较。
6.4.4 故障恢复与弹性训练
故障发生后的执行重构包含若干步骤：检测故障并确认故障范围、决定是否终止作业或保留健康进程、重新分配资源、定位可用检查点、按新的并行布局重分片、加载状态并继续训练。TrainMover（OSDI 2026）指出，大规模训练作业经常被硬件与软件异常以及运维事件中断，而既有的检查点重启或运行时重配置方案存在停机时间长、性能退化的缺点，因此恢复过程本身值得作为独立问题优化。衡量这类机制的核心指标是停机时间与重复计算量，其乘积决定了每次故障的实际损失。
缩短恢复时间的第一条路径是加快状态加载。ByteRobust（SOSP 2025）把最小化中断、高效诊断与有效容错作为生产基础设施的三个目标，其恢复流程与诊断结果直接衔接；ByteCheckpoint（NSDI 2025）通过重分片能力使检查点可以加载到与保存时不同的并行配置上，这也是节点替换后必须的能力。Characterization of Large Language Model Development in the Datacenter（NSDI 2024）与 MegaScale（NSDI 2024）的运营经验说明，恢复效率不仅取决于读写带宽，也取决于作业调度与资源能否及时到位。
第二条路径是把恢复范围限制在更小的故障域内。Gemini（SOSP 2023）用主机内存保存检查点以支撑快速恢复，其代价是恢复后仍需依赖持久存储中的较旧版本作为兜底；SWIFT（IEEE TPDS 2024）与 MoE 稀疏检查点工作则面向流水线或专家并行的局部恢复，使被替换的阶段只重载自身状态。故障域越小，需要重算和重载的数据越少，但恢复动作对全局同步的要求也越高，例如流水线并行中的单阶段回滚需要与上下游阶段协调进度。
第三条路径是避免让作业在故障后从零开始。热备节点替换以预先预热或弹性保留的机器接替故障节点，TrainMover（OSDI 2026）通过角色与状态迁移、通信关系切换和旧节点退出，实现最短停机与零内存开销；生产实践中运营商通常会保留一小部分备用或弹性 GPU 资源（公开资料中该比例约为 6%），因此这类机制本质上是用闲置容量换取恢复时间。变规模训练则走向另一个方向：Oobleck（SOSP 2023）采用规划与执行协同设计，预先构建异构流水线模板并实例化至少 f+1 个逻辑等价的流水线副本，从而可证明地容忍 f 个同时故障；ReCycle（SOSP 2024）不依赖备用服务器，而是利用分布式训练中固有的功能冗余，通过流水线自适应在故障后继续执行。两者分别以额外副本和运行时重配置换取容错能力，代价是资源效率或并行效率的下降。
综合来看，恢复与弹性机制需要在三个维度上权衡：停机时间、额外资源占用与训练语义的保持。语义保持尤其容易被忽略，节点数或并行配置变化后，数据并行的全局批量、优化器状态的分片方式与学习率调度都需要重新对齐，否则恢复出的作业与原作业并非同一训练过程（Universal Checkpointing，USENIX ATC 2025；Di-PS，NSDI 2026）。评价时应给出每次中断的平均停机时间、重算步数、额外资源比例以及扩展效率的变化，并说明这些数字对应的故障注入方式与作业规模。
6.4.5 在线推理高可用与SLO保障
在线推理的容错与训练不同：服务是有状态的，故障发生时不仅要恢复模型容量，还要处理在途请求已经累积的 KV 状态，并在此过程中维持延迟目标。评估这类系统需要使用一组固定口径，包括可用性、首 token 时延（TTFT）、每输出 token 时延（TPOT/ITL）、端到端延迟、goodput、SLO 违约率、恢复时间以及故障期的有效吞吐；其中 goodput 指在延迟约束下实际完成的服务量，比无约束吞吐更能反映故障期的真实服务能力（DistServe，OSDI 2024）。
实例故障转移需要同时解决资源效率与恢复速度。DéjàVu（ICML 2024）把分布式推理的低效归结为三个问题：预填充与逐 token 解码的双峰延迟在流水线并行部署中产生气泡、显存被过度预留、以及故障后的恢复时间过长；为此它通过统一的状态流式库实现预填充与解码分离、微批交换与状态复制，使容错建立在已经存在的数据通路之上。在成本敏感场景中，SpotServe（ASPLOS 2024）利用可随时被抢占的廉价实例提供服务，并提出以更细粒度提交推理进度的有状态恢复机制，使抢占后可以廉价续跑，在真实抢占轨迹上把 P99 尾延迟降低 2.4—9.1 倍。冷启动是另一类容量问题：ServerlessLLM（OSDI 2024）利用推理服务器上大量近 GPU 存储与内存保存模型检查点，减少远程下载；BlitzScale（OSDI 2025）则指出自动扩缩面临扩缩速度与参数缓存之间的根本权衡，数据面加载性能不足会让新实例在参数就绪前处于停滞，从而无法及时消除排队。
KV 状态的处理有三条可选路径：迁移现有状态、依据冗余重建、以及重新执行预填充。Llumnix（OSDI 2024）面向资源与延迟需求各异且难以预测的请求，通过跨实例调度与迁移在集群内重新分配负载，迁移的优势是保留已计算状态，代价是传输量随上下文长度增长。ServerlessLLM 的多级加载与 SkyPilot 类迁移机制说明近端存储可显著降低传输开销。GhostServe（MLSys 2026）代表重建路线：它以纠删码在主机内存中保存流式 KV 的校验分片，设备故障时快速重建丢失的状态，避免全量重算或大规模状态迁移。重新执行预填充则最不依赖额外机制，但在长上下文下代价最高，因此更适合短序列或对恢复时间不敏感的场景。
把容错做进正常运行路径会带来持续性开销，这也是复制类方案的共同代价。DéjàVu 的状态复制与 GhostServe 的纠删码分别代表完整复制与冗余编码两种思路，前者恢复最快但额外内存最多，后者在正常运行开销与恢复时间之间取得折中，而重新计算路线则以恢复时间换取零额外开销。选择依据是故障频率、可接受的中断时长、额外显存预算以及需要承受的同时故障数量；当服务承载长上下文与高并发请求时，KV 的复制规模本身可能成为新的容量瓶颈。
请求重调度与过载保护决定了故障或突发负载发生时系统能否维持 SLO。JITServe（NSDI 2026）对海量真实请求的分析以及用户研究与服务商访谈表明，请求可分为延迟敏感、截止时间敏感与复合依赖三种主导模式，各自关注不同指标，因此用统一策略调度会同时牺牲两类请求；AdaServe（EuroSys 2026）进一步指出，现代应用的 SLO 从交互式编码助手的低延迟到数据整理任务的宽松约束跨度很大，而依赖统一批处理的系统难以同时满足，需要针对多 SLO 的调度与批处理策略。在容量侧，KUNSERVE（EuroSys 2026）指出真实负载尖峰下 GPU 显存容易过载，等待 KV 回收造成的排队会使响应延迟上升一个数量级以上，因此需要以参数为中心的内存管理来应对过载；BlitzScale（OSDI 2025）则从扩缩速度一侧缓解容量不足。
评价在线推理的可靠性需要真实负载与分场景报告。ServeGen（NSDI 2026）指出，缺乏对生产工作负载的完整刻画会同时阻碍新场景的动机验证与基准设计，因此工作负载生成应尽量贴近真实到达过程与长度分布；ServeGen 与 StriaTrace（OSDI 2026）一类工作为线上异常评价提供了更现实的输入。报告结果时应区分稳态、过载与注入故障三种情形，并同时给出延迟分位数与 goodput，因为平均值会掩盖尾部的违约情况，而正是尾延迟决定了用户体验与 SLO 达成率。
